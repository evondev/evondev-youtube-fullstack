Docker & Compose — bản tra nhanh

Chỉ những lệnh bạn thật sự dùng khi làm backend. In ra dán cạnh màn hình.

🖨 In được (Cmd+P) · Đã kiểm chứng với Docker 28.0.1 + Compose v2.33.1 trên máy bạn.

🌉 Hiểu 3 danh từ này là hiểu hết Docker
  • Image — bản đóng gói bất biến (như file .zip cài đặt). Vd postgres:18-alpine.
  • Container — một tiến trình đang chạy sinh ra từ image. Xoá đi là mất sạch những gì ghi bên trong.
  • Volume — ổ đĩa do Docker quản lý, gắn vào container. Đây là thứ duy nhất sống sót khi container chết.

1. Vòng đời hằng ngày (99% thời gian bạn chỉ dùng 4 lệnh này)

LệnhLàm gìKhi nào dùng
docker compose up -dBật toàn bộ service khai báo trong docker-compose.yml, chạy nềnMỗi lần khởi động máy / bắt đầu code
docker compose psLiệt kê service đang chạy + trạng thái healthy + cổngĐầu tiên khi "sao app không nối được DB?"
docker compose logs -f postgresXem log, -f = bám theo liên tụcContainer chết / crash-loop
docker compose downTắt & xoá container, GIỮ volumeXong việc, muốn máy nhẹ
🚨 Một cờ đổi đời

docker compose down -v xoá luôn volume — tức toàn bộ database. Ở máy dev đây là nút "làm lại từ đầu". Trên server production đây là mất sạch dữ liệu khách hàng, không có Ctrl+Z. Trước khi gõ -v, luôn kiểm lại đang ở terminal nào.

2. Sự thật "Up ≠ sẵn sàng"

STATUS: Up 2 seconds chỉ nói tiến trình đã khởi động, không nói database đã nhận kết nối được. Khoảng chênh vài giây đó chính là chỗ app crash lúc khởi động. healthcheck trong compose là cách trả lời câu hỏi "sẵn sàng CHƯA?" bằng máy móc:

docker-compose.yml — mẫu đã chạy thật 
healthcheck:
  # Docker tự gõ lệnh này trong container; exit code 0 = khoẻ
  test: ['CMD-SHELL', 'pg_isready -U elearning -d elearning']
  interval: 5s   # bao lâu hỏi lại một lần
  timeout: 5s    # hỏi quá lâu không đáp thì coi như trượt
  retries: 10    # trượt liên tiếp 10 lần mới gắn cờ unhealthy

3. Chui vào bên trong container

bash 
# Mở shell trong container đang chạy. -it = interactive + cấp terminal
docker compose exec postgres sh

# Vào thẳng psql của DB dự án (khỏi cần cài client trên máy)
docker compose exec postgres psql -U elearning -d elearning

# Gõ lệnh redis mà không cần vào shell
docker compose exec redis redis-cli ping   # → PONG

# Nối từ MÁY BẠN vào (nhớ cổng đã map: 5433 chứ không phải 5432)
psql -h localhost -p 5433 -U elearning -d elearning
💡 Vì sao bên trong là 5432 mà bên ngoài là 5433?

Dòng '5433:5432' đọc là cổng-trên-máy-bạn : cổng-trong-container. Bên trong container Postgres vẫn nghe 5432 như mọi khi; ta chỉ đổi cửa bên ngoài vì 5432 trên máy bạn đã bị Postgres Homebrew chiếm. Hệ quả cần nhớ: app chạy trên máy bạn nối qua localhost:5433, còn một container khác trong cùng compose lại nối qua postgres:5432 (tên service, cổng trong) — nhầm hai cái này là lỗi kinh điển lúc đưa app vào Docker ở Bài 46.

4. Khi có sự cố — thứ tự chẩn đoán

#LệnhĐang tìm gì
1docker compose psNó có chạy không? Có healthy không? Cổng map đúng chưa?
2docker compose logs --tail=50 <service>Dòng lỗi cuối cùng trước khi chết
3docker compose restart <service>Chỉ khởi động lại tiến trình, không đụng dữ liệu
4lsof -i :5433Cổng có bị tiến trình khác chiếm không (lỗi bind/EADDRINUSE)
5docker compose down && docker compose up -dDựng lại container từ đầu, dữ liệu vẫn còn

5. Dọn dẹp (Docker ăn ổ cứng rất khoẻ)

bash 
# Xem Docker đang chiếm bao nhiêu GB và ở đâu
docker system df

# Dọn image/container/network KHÔNG còn dùng. An toàn với volume.
docker system prune

# ⚠️ Thêm --volumes là xoá cả volume mồ côi — có thể là DB của project khác!
docker system prune --volumes

# Liệt kê volume để biết mình sắp xoá cái gì (LÀM TRƯỚC khi prune)
docker volume ls

6. Bẫy đã cắn thật trong khoá này

⚠️ postgres:18 đổi chỗ gắn volume

Mọi tutorial cũ dạy gắn /var/lib/postgresql/data. Từ Postgres 18, PGDATA là /var/lib/postgresql/18/docker → gắn theo đường cũ thì container crash-loop. Đúng phải là postgres-data:/var/lib/postgresql. Bài học tổng quát cho cả khoá: đọc docs của đúng phiên bản bạn đang dùng, đừng copy tutorial 3 năm trước.
