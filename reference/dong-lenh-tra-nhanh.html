Đọc hiểu dòng lệnh — giải mã mọi khối copy-paste

Từ Bài 02 tới giờ bạn đã dán hàng chục khối curl và psql. Trang này giải thích từng ký tự trong đó — để lần sau bạn đọc chứ không dán mù.

🖨 In được (Cmd+P) · Mọi kết quả trong trang đã chạy thật trên máy bạn: macOS · curl 8.x · psql 18.3 · bash

🌉 Vì sao trang này quan trọng hơn nó trông có vẻ

Dán lệnh không hiểu thì lúc chạy đúng không sao. Vấn đề là lúc chạy sai. Bạn sẽ không biết lỗi ở API của mình, ở database, hay chỉ ở chỗ bạn gõ nhầm một dấu nháy — và sẽ mất hàng giờ sửa nhầm chỗ.

Ba thứ trong trang này gây mất thời gian nhiều nhất cho người mới: nháy đơn vs nháy kép, exit code, và VAR=x lệnh. Nắm ba cái đó là đọc được 90% khối lệnh trong khoá.

2. Nháy đơn vs nháy kép — thủ phạm số một

Trước khi curl nhìn thấy lệnh của bạn, shell đọc trước và sửa lại. Loại nháy quyết định shell được phép sửa những gì.

KiểuShell có nội suy không?Dùng khi
'nháy đơn'KHÔNG — giữ nguyên từng ký tựJSON, mật khẩu, chuỗi có $ hoặc "
"nháy kép"CÓ — thay $BIEN, $(lệnh)khi bạn muốn chèn giá trị biến vào
không nháyCÓ, và còn tách chuỗi theo khoảng trắngchỉ khi giá trị không có khoảng trắng
bash — chạy thử để thấy khác biệt 
PRICE=499000

echo "nháy kép : {\"price\": $PRICE}"
echo 'nháy đơn : {"price": $PRICE}'
kết quả THẬT 
nháy kép : {"price": 499000}     ← $PRICE đã bị thay bằng giá trị
nháy đơn : {"price": $PRICE}     ← giữ nguyên y hệt
🚨 Lỗi kinh điển: bọc JSON bằng nháy kép

JSON bản thân nó đã đầy dấu ". Bọc ngoài bằng " nữa là shell nuốt mất hết:

bash — hai lệnh, chỉ khác loại nháy bọc ngoài 
# ĐÚNG — nháy đơn bọc ngoài, dấu " bên trong sống sót
curl -s -X POST http://localhost:4477/ \
  -H 'Content-Type: application/json' \
  -d '{"title":"NestJS","price":499000}'

# SAI — nháy kép bọc ngoài
curl -s -X POST http://localhost:4477/ \
  -H 'Content-Type: application/json' \
  -d "{"title":"NestJS"}"
server THẬT nhận được gì (đã chạy) 
ĐÚNG → bodyServerNhanDuoc: "{\"title\":\"NestJS\",\"price\":499000}"

SAI  → bodyServerNhanDuoc: "{title:NestJS}"
                            ↑ MẤT SẠCH dấu " — JSON hỏng, API trả 400

Và đây là chỗ tốn thời gian nhất: API của bạn không hề sai. Bạn sẽ đi sửa DTO, sửa ValidationPipe, sửa controller — trong khi lỗi nằm ở một dấu nháy trong Terminal. JSON thì luôn bọc nháy đơn.

3. curl — cờ nào làm gì

CờLàm gìKhi nào dùng
-ssilent — tắt thanh tiến trìnhgần như luôn luôn, cho output sạch
-iin cả header phản hồixem status code, Content-Type
-X POSTđổi method (mặc định GET)tạo dữ liệu
-H '...'thêm một header gửi đibắt buộc khi gửi JSON
-d '...'gửi bodyPOST/PUT/PATCH
-o /dev/nullvứt body đichỉ quan tâm tốc độ / status
-w '...'in thông số sau khi xongđo status, thời gian

-vin cả request lẫn response thôkhi bí thật sự
bash — xem header phản hồi 
curl -s -i http://localhost:4455/
kết quả THẬT 
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 28 Aug 2026 09:24:08 GMT
Connection: keep-alive
Keep-Alive: timeout=5

-w in ra thông số về cuộc gọi, không phải nội dung. Ghép với -o /dev/null thành công cụ đo nhanh:

bash 
curl -s -o /dev/null -w 'code=%{http_code} time=%{time_total}s size=%{size_download}\n' \
  http://localhost:4455/
kết quả THẬT 
code=200 time=0.000767s size=11
⚠️ Quên -H 'Content-Type: application/json' thì sao?

curl không tự đoán là JSON. Mặc định nó khai application/x-www-form-urlencoded — đã kiểm chứng thật. Nest nhìn header đó, không parse JSON, nên @Body() rỗng và ValidationPipe trả 400 dù JSON bạn gửi hoàn toàn đúng. Gửi JSON thì -H là bắt buộc, không phải tuỳ chọn.

4. Exit code — con số nói lỗi nằm ở đâu

Mọi lệnh khi kết thúc đều trả một con số. 0 = thành công, khác 0 = có chuyện. Con số này quý ở chỗ nó phân biệt lỗi mạng với lỗi ứng dụng.

bash — đọc exit code của lệnh vừa chạy 
curl -s http://localhost:9999/
echo "exit=$?"          # $? = exit code của lệnh NGAY TRƯỚC
kết quả THẬT 
exit=7
Exit codeNghĩaNghĩa với bạn
0xong xuôicurl gọi được — kể cả khi API trả 404/500
7không kết nối đượcserver chưa chạy, hoặc sai port
52server không trả gìprocess chết giữa chừng (Bài 02!)
6không phân giải được tên miềngõ sai host, hoặc mất mạng
28hết giờ chờserver treo, hoặc đang bận CPU (Bài 03)
💡 Vì sao API trả 500 mà exit code vẫn là 0

Vì curl chỉ chịu trách nhiệm chuyển thư. Thư giao tận tay là nhiệm vụ hoàn thành — nội dung thư báo tin xấu là chuyện của bạn với server, không phải lỗi của curl.

Nên: exit code nói về đường truyền, status code nói về ứng dụng. Muốn kiểm status trong script thì dùng -w '%{http_code}', đừng dựa vào $?.

5. VAR=x lệnh — biến chỉ sống một lần

Hai cách đặt biến, khác nhau ở tuổi thọ:

bash 
# Cách 1 — gán TRƯỚC tên lệnh: chỉ lệnh đó thấy, xong là biến mất
MY_TOKEN=abc123 sh -c 'echo "trong lệnh: $MY_TOKEN"'
echo "lệnh sau:  [$MY_TOKEN]"
kết quả THẬT 
trong lệnh: abc123
lệnh sau:  []          ← rỗng: biến đã chết cùng lệnh trước
bash 
# Cách 2 — export: sống tới khi đóng cửa sổ Terminal
export PGPASSWORD=elearning_dev_pw
psql -h localhost -p 5433 -U elearning -d elearning -c "\dt"
psql -h localhost -p 5433 -U elearning -d elearning -c "SELECT 1;"
# cả hai lệnh trên đều dùng lại mật khẩu đó
🔎 Chọn cái nào

Chạy một lệnh → gán trước tên lệnh (an toàn hơn, không sót mật khẩu trong phiên). Chạy nhiều lệnh liên tiếp → export một lần cho đỡ lặp.

Cả hai đều không sống qua cửa sổ Terminal mới. Mở tab mới mà psql hỏi mật khẩu thì đó là lý do — không phải hỏng gì cả.

Nó đang chờ bạn gõ mật khẩu nhưng không hiện chữ nào (kể cả dấu *) — đó là cố ý, để không ai đọc trộm. Cứ gõ rồi Enter. Hoặc dùng PGPASSWORD= ở mục 5 để khỏi bị hỏi. Sai mật khẩu thì exit code là 2 kèm dòng password authentication failed.

7. Heredoc — dán nhiều dòng vào một lệnh

Khi cần đưa cả khối SQL nhiều dòng vào psql, viết trên một dòng thì không đọc nổi. Heredoc là cú pháp "mọi thứ từ đây tới chữ kết thúc là dữ liệu đầu vào":

bash 
psql -h localhost -p 5433 -U elearning -d elearning <<'SQL'
  INSERT INTO users (email, full_name)
  VALUES ('a@example.com', 'Học viên A');
SQL
🚨 Dấu nháy quanh 'SQL' không phải cho đẹp

Nó quyết định shell có được sửa nội dung bên trong hay không — y hệt quy tắc ở mục 2:

bash — hai heredoc, chỉ khác cặp nháy 
PRICE=499000

cat <<'END'
không nội suy: $PRICE và $(date +%Y)
END

cat <<END
có nội suy   : $PRICE và $(date +%Y)
END
kết quả THẬT 
không nội suy: $PRICE và $(date +%Y)     ← nguyên xi
có nội suy   : 499000 và 2026            ← shell đã thay hết

Với SQL thì luôn dùng <<'SQL' có nháy. Không có nháy mà SQL của bạn chứa $ (chuỗi có ký tự đó, hàm PostgreSQL dùng $$...) là shell nuốt mất, câu lệnh sai một cách khó hiểu.

8. Nối lệnh: |, >, 2>&1, &&

Ký hiệuLàm gìVí dụ đã dùng trong khoá

💡 Vì sao có 2>&1 — hai luồng ra khác nhau

Mỗi lệnh có hai đường ra: stdout (số 1, kết quả bình thường) và stderr (số 2, thông báo lỗi). Trên màn hình chúng trộn lẫn nên bạn tưởng là một.

> out.txt chỉ bắt luồng 1. Nên khi lệnh hỏng, file rỗng còn lỗi thì vẫn nhảy ra màn hình. 2>&1 nghĩa là "đổ luồng 2 vào chỗ luồng 1 đang chảy" — từ đó file bắt được cả hai.

bash — chứng minh 
ls khong-ton-tai.txt > out.txt 2>&1
echo "exit=$?"
cat out.txt
kết quả THẬT 
exit=1
ls: khong-ton-tai.txt: No such file or directory   ← lỗi đã VÀO file
bash — && và ; khác nhau thế nào 
false && echo "không bao giờ in"; echo "&& : đã bỏ qua"
false ; echo "; : vẫn chạy"
kết quả THẬT 
&& : đã bỏ qua
; : vẫn chạy

9. xargs -P — bắn nhiều request cùng lúc

Đây là dòng bạn đã dán ở Bài 09 mà chưa ai giải thích:

mổ xẻ 
seq 5 | xargs -P5 -I{} curl -s -o /dev/null http://localhost:3333/courses
└──┬──┘   └─┬──┘ └──┬─┘ └───────────────┬──────────────────────┘
   │        │       │                   │
in 1..5   chạy   chỗ thay          lệnh chạy 5 lần
       5 tiến trình  số vào
        SONG SONG  (ở đây không dùng)
bash — đo thật, server mỗi request chờ 1 giây 
time (seq 5 | xargs -P1 -I{} curl -s -o /dev/null http://localhost:4466/)
time (seq 5 | xargs -P5 -I{} curl -s -o /dev/null http://localhost:4466/)
kết quả THẬT 
-P1 (tuần tự)  real  0m5.132s     ← 5 × 1 giây, xếp hàng
-P5 (song song) real  0m1.028s     ← cả 5 chờ CÙNG LÚC

Con số này chính là bài học Bài 03 nhìn từ phía client: 5 request I/O chờ song song vẫn hết ~1 giây, vì chờ không tốn CPU.

10. Khi kẹt — bốn câu hỏi theo thứ tự

#HỏiKiểm bằng
1Server có đang chạy không?exit code 7 = chưa chạy · lsof -i :3333
2Có gọi đúng cổng không?API 3333 · Postgres 5433 · Redis 6379
3Request đi tới nơi chứ?-i xem status · 0 + 404 = tới rồi, sai đường dẫn
4Body có nguyên vẹn không?nháy đơn chưa? có -H Content-Type chưa?
bash — bộ lệnh cấp cứu 
# Ai đang giữ cổng 3333?
lsof -i :3333

# Giết tiến trình cũ còn sót (hay gặp khi restart Nest)
lsof -ti :3333 | xargs kill -9

# Container còn sống không?
docker ps --filter name=elearning-postgres

# Xem log container
docker logs --tail 50 elearning-postgres

# Kiểm nhanh API còn thở không (chỉ in status)
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3333/courses
🔎 Ba phím tắt Terminal đáng nhớ nhất

Ctrl+C dừng lệnh đang chạy · Ctrl+R tìm lại lệnh đã gõ (gõ vài chữ là ra) · Ctrl+L xoá màn hình. Phím ↑ lấy lại lệnh trước — bạn sẽ dùng nó nhiều nhất trong đời làm backend.
