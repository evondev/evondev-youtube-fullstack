Module 3 · Bài 11

Thiết kế schema e-learning: cái gì được đổi, cái gì phải bất biến

Vẽ bảng cho đủ là phần dễ. Phần khó — và phần tốn tiền nếu sai — là biết dữ liệu nào không bao giờ được phép thay đổi.

⏱ ~40 phút · 🎯 Sản phẩm: 6 bảng thật trong Postgres của bạn, và một thí nghiệm chứng minh hoá đơn cũ không đổi khi bạn giảm giá.

🌉 Bắc cầu — bạn đã trả lời một nửa rồi

Tôi hỏi: giá tiền lưu ở đâu? Bạn trả lời "lưu ở khoá học". Đúng — nhưng chỉ đúng một nửa, và nửa còn lại là chỗ mất tiền thật.

Bài này bắt đầu từ chính chỗ đó. Vì schema là quyết định khó sửa nhất trong cả hệ thống: code viết sai thì sửa rồi deploy lại; schema thiết kế sai thì tới lúc phát hiện, dữ liệu cần thiết chưa từng được ghi — không có gì để phục hồi.

1. Tìm thực thể: đọc nghiệp vụ, khoanh danh từ

Cách bắt đầu đơn giản nhất: viết nghiệp vụ ra bằng tiếng Việt, rồi khoanh các danh từ.

nghiệp vụ e-learning 
"Một NGƯỜI DÙNG đăng ký tài khoản, xem danh sách KHOÁ HỌC.
 Mỗi khoá có nhiều BÀI HỌC.
 Người dùng tạo ĐƠN HÀNG để mua một hoặc nhiều khoá.
 Thanh toán xong thì được GHI DANH và học được."

Sáu danh từ → sáu bảng. Nhưng chú ý hai cái cuối, chúng khác nhau về bản chất:

💡 Hai loại dữ liệu — phân biệt được là nắm nửa bài này

Dữ liệu TRẠNG THÁI mô tả hiện tại đang thế nào: giá khoá học hôm nay, tên người dùng hôm nay. Sửa đè lên là đúng.

Dữ liệu SỰ KIỆN ghi lại chuyện đã xảy ra lúc đó: A trả 499.000 vào ngày 01/10. Quá khứ thì không sửa được — nên bảng ghi nó cũng không được phép đổi.

Gần như mọi bug dữ liệu nghiêm trọng trong hệ thống thanh toán đều đến từ việc lẫn lộn hai loại này.

2. Ba kiểu quan hệ, và khoá ngoại sống ở đâu

KiểuVí dụKhoá ngoại đặt ở đâu
1 — n1 khoá có n bài họcbên "nhiều": lessons.course_id
n — nn học viên ↔ n khoábảng thứ ba: enrollments
1 — 1user ↔ hồ sơ chi tiếtbên nào cũng được (hiếm dùng)
💡 Vì sao khoá ngoại luôn nằm bên "nhiều"

Thử làm ngược xem: để courses giữ danh sách bài học thì phải nhét nhiều giá trị vào một ô — mà một ô chỉ chứa được một giá trị. Còn để ở lessons.course_id thì mỗi bài học chỉ cần trỏ về đúng một khoá. Bên "nhiều" giữ khoá vì mỗi dòng của nó chỉ thuộc về một cha. Đó cũng là lý do quan hệ n–n bắt buộc phải có bảng thứ ba: cả hai bên đều "nhiều", không bên nào nhét vừa.

3. Viết schema thật

Ta viết bằng SQL thuần, chạy thẳng vào Postgres. Prisma sẽ tới ở bài sau — nhưng giống như Module 1 với node:http, thấy tận mắt tầng dưới rồi thì lát nữa Prisma chỉ là lớp tiện nghi, không phải hộp đen.

Tạo file elearning-api/db/schema.sql:

bash 
cd ~/Documents/youtube/fullstack/elearning-api
mkdir -p db
elearning-api/db/schema.sql 
-- ══════════════════ NGƯỜI DÙNG ══════════════════
CREATE TABLE users (
  -- GENERATED ALWAYS AS IDENTITY: Postgres tự cấp id, và CẤM ta tự gán.
  -- Cấm là có chủ ý — tự gán tay là nguồn gốc của id trùng.
  id         BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      TEXT        NOT NULL UNIQUE,
  full_name  TEXT        NOT NULL,
  -- TIMESTAMPTZ (có múi giờ), KHÔNG dùng TIMESTAMP trần.
  -- Server ở Singapore, khách ở VN — thiếu múi giờ là lệch 1 tiếng, âm thầm.
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ══════════════════ KHOÁ HỌC ══════════════════
CREATE TABLE courses (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title         TEXT   NOT NULL,
  -- CHECK = ràng buộc sống trong DATABASE, không phải trong code.
  -- Ai ghi thẳng bằng psql cũng bị chặn — DTO ở Bài 06 không làm được điều đó.
  level         TEXT   NOT NULL CHECK (level IN ('beginner', 'advanced')),
  -- Tên là current_price chứ không phải price: nói rõ đây là giá HÔM NAY.
  -- NUMERIC cho tiền, tuyệt đối không dùng float (xem cảnh báo bên dưới).
  current_price NUMERIC(12,0) NOT NULL CHECK (current_price >= 0),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ══════════════════ BÀI HỌC (1 khoá — n bài) ══════════════════
CREATE TABLE lessons (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  -- ON DELETE CASCADE: xoá khoá thì bài học trong đó đi theo.
  -- Hợp lý vì bài học KHÔNG tồn tại độc lập với khoá.
  course_id BIGINT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  title     TEXT   NOT NULL,
  position  INT    NOT NULL,
  -- Trong CÙNG một khoá không được có hai bài cùng vị trí.
  UNIQUE (course_id, position)
);

-- ══════════════════ ĐƠN HÀNG (1 user — n đơn) ══════════════════
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  -- ON DELETE RESTRICT: CẤM xoá user còn đơn hàng.
  -- Sổ sách kế toán không được phép bốc hơi vì ai đó bấm nhầm nút xoá.
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  status      TEXT   NOT NULL CHECK (status IN ('pending','paid','refunded')),
  total_price NUMERIC(12,0) NOT NULL CHECK (total_price >= 0),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ═══════════ DÒNG ĐƠN HÀNG — ĐÂY LÀ CHỖ CHỤP ẢNH ═══════════
CREATE TABLE order_items (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id     BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  course_id    BIGINT NOT NULL REFERENCES courses(id) ON DELETE RESTRICT,
  -- HAI DÒNG DƯỚI LÀ TRỌNG TÂM CẢ BÀI.
  -- Chúng SAO CHÉP giá và tên tại thời điểm mua, thay vì trỏ sang courses.
  -- Trông như dữ liệu thừa — nhưng đây là dữ liệu KHÁC BẢN CHẤT, xem phần 5.
  course_title TEXT   NOT NULL,
  unit_price   NUMERIC(12,0) NOT NULL CHECK (unit_price >= 0),
  -- Một đơn không được chứa cùng một khoá hai lần.
  UNIQUE (order_id, course_id)
);

-- ══════════════ GHI DANH (n — n) ══════════════
CREATE TABLE enrollments (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  course_id   BIGINT NOT NULL REFERENCES courses(id) ON DELETE RESTRICT,
  enrolled_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  -- Trái tim của bảng n-n: một người KHÔNG ghi danh hai lần cùng một khoá.
  -- Thiếu dòng này là bug "mua hai lần" mà code rất khó chặn cho kín.
  UNIQUE (user_id, course_id)
);
🚨 NUMERIC cho tiền — đừng bao giờ dùng float

Chạy thử ngay — dán cả khối này vào Terminal (không phải vào file .sql). Postgres từ Bài 00 phải đang chạy; chưa có bảng nào cũng chạy được vì câu này không đọc bảng.

bash — dán vào Terminal 
PGPASSWORD=elearning_dev_pw psql -h localhost -p 5433 -U elearning -d elearning -c "
SELECT (0.1::numeric + 0.2::numeric) AS numeric_result,
       (0.1::float8  + 0.2::float8)  AS float_result;"
kết quả THẬT trên Postgres 18.4 
 numeric_result |    float_result
----------------+---------------------
            0.3 | 0.30000000000000004
(1 row)                ↑ sai từ chữ số thứ 17

Số lẻ nhỏ xíu, nhưng cộng qua hàng triệu giao dịch thì sổ sách không bao giờ khớp với cổng thanh toán — và bạn sẽ mất nhiều ngày đi tìm "tiền thất thoát" không tồn tại. float lưu xấp xỉ theo cơ số 2; NUMERIC lưu chính xác theo cơ số 10. Tiền bạc không có chỗ cho xấp xỉ.

🔎 Lỡ chạy hai lần thì sao?

Lần hai sẽ báo relation "users" already exists — không hỏng gì cả, chỉ là đã có rồi. Muốn làm lại từ đầu: DROP TABLE IF EXISTS enrollments, order_items, orders, lessons, courses, users CASCADE; Chú ý thứ tự ngược: bảng nào trỏ tới bảng khác thì phải xoá trước.

5. Thí nghiệm quyết định: giảm giá rồi xem hoá đơn cũ

Đây là chỗ trả lời trọn vẹn câu hỏi mở đầu. Dựng một lần mua:

bash — dán cả khối vào psql 
psql -h localhost -p 5433 -U elearning -d elearning <<'SQL'
INSERT INTO users(email,full_name) VALUES ('a@hv.vn','Hoc Vien A');
INSERT INTO courses(title,level,current_price)
  VALUES ('NestJS Fundamentals','beginner',499000);
INSERT INTO orders(user_id,status,total_price) VALUES (1,'paid',499000);

-- CHỤP giá + tên tại thời điểm mua, thay vì chỉ trỏ tới courses
INSERT INTO order_items(order_id,course_id,course_title,unit_price)
  SELECT 1, id, title, current_price FROM courses WHERE id=1;

INSERT INTO enrollments(user_id,course_id) VALUES (1,1);
SQL

Giờ chạy sale — giảm giá và đổi luôn tên khoá:

bash 
psql -h localhost -p 5433 -U elearning -d elearning -c "
UPDATE courses SET current_price=199000, title='NestJS Fundamentals 2027' WHERE id=1;"

# Hoá đơn cũ giờ ghi gì?
psql -h localhost -p 5433 -U elearning -d elearning -c "
SELECT course_title, unit_price FROM order_items WHERE order_id=1;"
kết quả THẬT (đã chạy trên Postgres 18.4) 
giá hiện tại của khoá : 199000
tên hiện tại của khoá : NestJS Fundamentals 2027

hoá đơn của học viên A: NestJS Fundamentals - 499000 đ   ← KHÔNG đổi
đã trả                : 499000 đ

tổng doanh thu        : 499000 đ   ← KHÔNG đổi dù giá đã giảm
💡 Nếu order_items chỉ lưu course_id thì sao

Hoá đơn sẽ hiện 199.000 — trong khi ngân hàng đã trừ của A 499.000. Kéo theo:

  • Đối soát lệch — sổ sách một đằng, cổng thanh toán một nẻo
  • Hoàn tiền sai — trả lại 199.000 cho người đã đóng 499.000
  • Doanh thu quá khứ tự đổi — báo cáo tháng 10 chạy lại hôm nay ra con số khác hôm qua

Không có sự cố nào, không có lỗi nào trong log. Chỉ là số liệu tài chính âm thầm sai — loại bug tệ nhất vì không ai phát hiện cho tới khi kiểm toán.

⚠️ "Lưu hai chỗ là dữ liệu thừa, phạm chuẩn hoá" — nghe rất có lý và rất sai

Chuẩn hoá (normalization) bảo: đừng lưu cùng một sự thật ở hai nơi. Nhưng courses.current_price và order_items.unit_price là hai sự thật khác nhau:

đọc kỹ hai câu này 
courses.current_price     = "hôm nay khoá này bán bao nhiêu"
order_items.unit_price    = "ngày 01/10 người ta ĐÃ TRẢ bao nhiêu"

Chúng tình cờ bằng nhau tại thời điểm mua, rồi đường ai nấy đi. Đây không phải dữ liệu thừa — đây là dữ liệu khác bản chất mà tình cờ có cùng giá trị một lúc. Nhận ra khác biệt đó là ranh giới rất rõ giữa người học thuộc quy tắc chuẩn hoá và người hiểu nó dùng để làm gì.

6. Ràng buộc: để database tự bảo vệ mình

Bài 06 bạn đã validate ở tầng API bằng DTO. Vậy sao còn cần CHECK, UNIQUE, REFERENCES trong database? Vì API không phải cửa duy nhất vào dữ liệu: còn có script chạy tay, công cụ quản trị, đồng nghiệp gõ psql lúc nửa đêm, và chính bạn lúc sửa dữ liệu gấp.

Thử phá — tôi đã chạy đủ 8 ca này, tất cả đều bị chặn:

Thử làm bậyPostgres trả lời
Ghi danh trùng cùng một khoáduplicate key ... enrollments_user_id_course_id_key
Ghi danh vào khoá không tồn tạiviolates foreign key constraint
Email trùngduplicate key ... users_email_key
level = 'trung-cap'violates check constraint courses_level_check
Giá âmviolates check constraint
Hai bài học cùng vị trí 1duplicate key ... lessons_course_id_position_key
Tự gán idcannot insert a non-DEFAULT value into column "id"
Xoá khoá đã có người muaviolates RESTRICT setting of foreign key
💡 CASCADE vs RESTRICT — chọn theo nghĩa, đừng chọn cho tiện
ON DELETE CASCADEON DELETE RESTRICT
Nghĩaxoá cha → con đi theocòn con → cấm xoá cha
Dùng khicon không tồn tại độc lậpcon là bằng chứng phải giữ
Trong bàilessons theo coursesorders theo users, order_items theo courses

Đặt CASCADE cho orders → users nghĩa là xoá một tài khoản sẽ xoá sạch lịch sử thanh toán của họ. Một cú bấm nhầm là mất sổ sách, không phục hồi được. Với dữ liệu tiền bạc, mặc định luôn là RESTRICT.

7. Câu hỏi tư duy (bắc cầu sang Bài 12)

Schema đã có, nhưng nó mới chỉ nằm trong một file .sql bạn chạy tay. Hai câu hỏi:

Một: tháng sau bạn cần thêm cột courses.description. Sửa schema.sql rồi chạy lại? Nhưng chạy lại sẽ báo "table already exists". Mà database production thì đang có dữ liệu thật — không thể xoá đi tạo lại. Làm sao thay đổi cấu trúc một database đang chạy mà không mất dữ liệu?

Hai: bạn sửa trên máy mình. Đồng nghiệp cũng sửa trên máy họ. Production thì đang ở phiên bản cũ hơn cả hai. Ai biết database nào đang ở trạng thái nào?

Câu trả lời là migration — và nó chính là "git cho cấu trúc database".
