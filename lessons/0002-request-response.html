Module 1 · Bài 02

Request & Response: method, status code, header, body

Bài 01 server trả 200 cho mọi thứ. Bài này nó biết mình đang trả lời ai, cái gì, và vì sao.

⏱ ~40 phút · 🎯 Mục tiêu: đọc được body của một POST đến từng khúc, định tuyến theo method + đường dẫn, và trả đúng mã trạng thái thay vì 200 cho tất cả.

🌉 Bắc cầu từ Bài 01

Cuối Bài 01 tôi hỏi: khi client gửi POST kèm một cục JSON, cục JSON đó nằm ở đâu trong request? Bạn thử console.log(request.body) và nhận undefined.

Bài này trả lời câu đó. Và trả lời luôn một thứ khác: ở bài tập Bài 01, server của bạn gọi / thì ra Trang chu, nhưng gọi /?q=1 lại ra Nothing. Không phải bạn gõ nhầm — bạn đã tin vào một thứ nói dối.

Câu chốt mang theo cả bài: một handler đúng đắn làm đúng 2 việc — phân giải request cho đúng (method + đường dẫn + body), rồi trả lời có chủ đích (status + header + body). Bài 01 bạn mới làm được nửa sau, và làm sai.

1. request.url nói dối — nó không phải đường dẫn

Ở Bài 01 bạn viết if (request.url === '/'). Nghe rất hợp lý. Nhưng hãy nhìn lại cái tên: nó là url, không phải path. Và theo docs Node về message.url, nó chứa "chỉ phần URL có mặt trong request HTTP thật" — tức là nguyên văn, dính cả query string.

Mở terminal và tự chứng minh, không cần server nào:

bash — chạy thẳng, không cần file 
node -e "console.log('/courses?level=beginner' === '/courses')"
kết quả THẬT (Node v22.18.0) 
false

Đó chính xác là con bug ở bài tập Bài 01. Chuỗi '/ping?a=1' không bao giờ bằng '/ping', nên request rơi tuột xuống nhánh mặc định.

💡 Vì sao Node không tự tách sẵn cho bạn?

Vì node:http cố ý dừng ở mức giao thức, không leo lên mức ứng dụng. Nó đưa bạn đúng những byte đã đi qua dây, không diễn giải hộ. Diễn giải là việc của tầng trên — và đó chính là cái Express/NestJS làm giúp bạn. Mỗi tiện nghi bạn dùng sau này đều là một việc ai đó đã làm ở đây; bạn đang học chính cái việc đó.

Cách tách đúng là new URL() — chuẩn web, có sẵn trong Node, chính docs Node khuyến nghị dùng. Nó cần một "gốc" (domain) vì request.url không có domain, nên ta ghép tạm từ header Host:

console.log('pathname      :', url.pathname);
console.log('level         :', url.searchParams.get('level'));
console.log('page          :', url.searchParams.get('page'));

🔎 Để ý cái dòng cuối

Tham số không tồn tại trả về null, không phải undefined và không ném lỗi. Nhớ kỹ: ở backend, mọi thứ đến từ client đều là tuỳ chọn cho tới khi bạn tự bắt buộc nó. Người dùng thật sẽ gọi API của bạn thiếu tham số, thừa tham số, sai kiểu — và họ không hề cố ý phá bạn.

2. Định tuyến thật = method + đường dẫn

Bài 01 bạn chỉ nhìn đường dẫn. Nhưng GET /courses (xem danh sách) và POST /courses (tạo mới) là hai việc hoàn toàn khác nhau ở cùng một đường dẫn. Đó là bản chất của REST: đường dẫn nói "cái gì", method nói "làm gì với nó".

Tạo file lab/02-request-response.mjs trong editor và dán nội dung dưới đây. Đây là file chính của cả bài — ta sẽ mổ từng phần ngay sau:

elearning-api/lab/02-request-response.mjs 
import { createServer } from 'node:http';

// Handler là async vì phần đọc body ở dưới cần `await`.
const server = createServer(async (request, response) => {
  // request.url là CHUỖI THÔ, dính cả query string ('/courses?level=beginner').
  // new URL() tách nó ra thành pathname + searchParams cho ta.
  // Tham số thứ 2 là "gốc" bắt buộc, vì request.url không có domain.
  const url = new URL(request.url, `http://${request.headers.host}`);
  const pathname = url.pathname;
  const method = request.method;

  console.log(`${method} ${pathname}`);

  // ── Route 1: GET /ping ─────────────────────────────────
  if (method === 'GET' && pathname === '/ping') {
    response.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    return response.end('pong');
  }

  // ── Route 2: GET /courses?level=... ────────────────────
  if (method === 'GET' && pathname === '/courses') {
    // ?? 'all' = giá trị mặc định khi client không gửi tham số.
    const level = url.searchParams.get('level') ?? 'all';
    response.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    return response.end(JSON.stringify({ level, items: [] }));
  }

  // ── Route 3: POST /courses — đọc body ──────────────────
  if (method === 'POST' && pathname === '/courses') {
    // request LÀ một stream: dữ liệu tới theo từng khúc, không có sẵn.
    let raw = '';
    for await (const chunk of request) {
      raw += chunk;
    }

    let data;
    try {
      data = JSON.parse(raw);
    } catch {
      // Client gửi rác → lỗi của CLIENT → 400, không phải 500.
      response.writeHead(400, { 'Content-Type': 'application/json; charset=utf-8' });
      return response.end(JSON.stringify({ error: 'Invalid JSON body' }));
    }

    if (!data.title) {
      response.writeHead(400, { 'Content-Type': 'application/json; charset=utf-8' });
      return response.end(JSON.stringify({ error: 'Missing field: title' }));
    }

    // 201 = "đã tạo ra tài nguyên mới". Location chỉ tới nơi nó vừa sinh ra.
    response.writeHead(201, {
      'Content-Type': 'application/json; charset=utf-8',
      Location: '/courses/1',
    });
    return response.end(JSON.stringify({ id: 1, title: data.title }));
  }

  // ── Đúng đường dẫn nhưng sai method → 405 ──────────────
  // Chú ý: nhánh này nằm SAU cùng của nhóm /courses, nên chỉ chạy khi
  // đường dẫn khớp mà không method nào ở trên nhận.
  if (pathname === '/courses') {
    response.writeHead(405, {
      'Content-Type': 'application/json; charset=utf-8',
      // RFC BẮT BUỘC có header Allow trong response 405.
      Allow: 'GET, POST',
    });
    return response.end(JSON.stringify({ error: `Method ${method} not allowed here` }));
  }

  // ── Không khớp gì cả → 404 ─────────────────────────────
  // Nhánh này là "lưới an toàn": mọi request lọt tới đây đều CÓ response.
  response.writeHead(404, { 'Content-Type': 'application/json; charset=utf-8' });
  response.end(JSON.stringify({ error: 'Not found' }));
});

server.listen(3337, () => {
  console.log('Server listening on http://localhost:3337');
});

3. Body là một dòng chảy, không phải một biến

Đây là câu trả lời cho câu hỏi tư duy Bài 01. Vì sao Node đưa sẵn request.method và request.url mà không đưa sẵn request.body?

Nhớ lại giải phẫu HTTP ở Bài 01: request line và header đi tới TRƯỚC, body đi tới SAU. Khi Node gọi handler của bạn, nó mới chỉ đọc xong phần đầu — body có thể còn đang trên đường, có thể là 20 byte, cũng có thể là một file 2GB. Node không dám đợi cho đủ rồi mới gọi bạn, vì như thế một người upload file lớn sẽ giam server lại.

Nên nó đưa bạn cái vòi thay vì cái xô. Theo docs Node: IncomingMessage Extends: stream.Readable — bản thân request là một stream.

Nhìn tận mắt. Tạo file lab/02-body-stream.mjs:

elearning-api/lab/02-body-stream.mjs 
import { createServer } from 'node:http';

const server = createServer(async (request, response) => {
  let chunkCount = 0;
  let totalBytes = 0;

  // `request` LÀ một stream đọc được. Vòng lặp này chạy MỖI KHI một khúc dữ liệu
  // vừa tới nơi qua dây mạng — không phải chạy một lần trên toàn bộ body.
  for await (const chunk of request) {
    chunkCount++;
    totalBytes += chunk.length;
  }

  console.log(`Received ${chunkCount} chunks, ${totalBytes} bytes total`);

  response.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  response.end(`chunks=${chunkCount} bytes=${totalBytes}\n`);
});

server.listen(3338, () => {
  console.log('Chunk counter listening on http://localhost:3338');
});

💡 Ba con số này nói gì
  • 5 byte → 1 khúc. Nhỏ thì tới một phát, nên bạn dễ tưởng body luôn "có sẵn".
  • 5MB → 82 khúc. Vòng lặp chạy 82 lần. Nếu bạn chạy lại có thể ra 81 hay 83 — và đó mới là điểm đáng nhớ nhất: số khúc phụ thuộc mạng và bộ đệm hệ điều hành, không phải thứ bạn kiểm soát. Đừng bao giờ viết code giả định "chắc nó về một lần".
  • GET → 0 khúc. Vòng lặp không chạy lần nào và cũng không treo — stream kết thúc ngay.
🎯 Chốt lại câu hỏi của Bài 01

method và url có sẵn vì chúng đã tới rồi (nằm ở dòng đầu). body không có sẵn vì nó chưa chắc đã tới. Cái mà mọi framework gọi là "body parser" chính xác là 6 dòng gom khúc bạn vừa viết, cộng thêm JSON.parse. Không hơn. Bạn vừa tự viết một body parser.

4. Thí nghiệm bắt buộc: một request rác giết cả server

Ở phần 2 tôi bọc JSON.parse trong try/catch. Nghe như chuyện "cẩn thận cho lành". Không — bỏ nó đi thì cả server chết, và bạn phải thấy tận mắt một lần.

Ở tab 2, bấm Ctrl+C tắt server đếm khúc. Sửa lab/02-body-stream.mjs thành:

elearning-api/lab/02-body-stream.mjs — bản CỐ Ý VIẾT SAI 
import { createServer } from 'node:http';

const server = createServer(async (request, response) => {
  let raw = '';
  for await (const chunk of request) {
    raw += chunk;
  }

  // CỐ Ý KHÔNG try/catch — để thấy hậu quả thật.
  const data = JSON.parse(raw);

  response.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
  response.end(JSON.stringify(data));
});

server.listen(3338, () => {
  console.log('Server listening on http://localhost:3338');
});

Một người lạ gõ 3 ký tự rác, và toàn bộ tiến trình server thoát. Không chỉ request đó hỏng — mọi user đang online đều mất kết nối. Lần gọi thứ 3 nhận exit=7 (connection refused): không còn tiến trình nào lắng nghe nữa.

Vì sao khắc nghiệt vậy? Handler của bạn là async, nên lỗi ném ra biến thành một promise bị từ chối mà không ai bắt. Từ Node 15, mặc định của tình huống này là giết tiến trình (trước kia chỉ cảnh báo). Node coi việc chạy tiếp với một lỗi bị nuốt là nguy hiểm hơn việc chết.

Đối chiếu với Bài 01: quên response.end() làm một client treo, server vẫn sống. Ném lỗi trong handler async làm tất cả client chết. Hai mức độ khác nhau, cùng một gốc: bạn phải chịu trách nhiệm cho mọi nhánh có thể xảy ra, kể cả nhánh do người khác gây ra. Đây chính là vấn đề mà exception filter của Nest (Bài 12) sinh ra để giải quyết — giờ thì bạn đã biết nó cứu bạn khỏi cái gì.

Sửa lại lab/02-body-stream.mjs về bản đếm khúc ban đầu (hoặc thêm try/catch vào) trước khi đi tiếp.

5. Status code: nói cho đúng, đừng trả 200 cho tất cả

Bài 01 server bạn trả 200 kể cả khi đường dẫn không tồn tại. Với con người thì trông vẫn "chạy được"; với máy thì đó là nói dối. Mà API tồn tại để nói chuyện với máy.

💡 Cách nhớ status code mà không cần học thuộc

Chỉ cần nhớ chữ số đầu tiên = ai đang nói và tình hình ra sao: 2xx "xong rồi" · 3xx "đi chỗ khác mà lấy" · 4xx "bạn sai" · 5xx "tôi sai". Ranh giới 4xx/5xx là ranh giới quan trọng nhất trong đời vận hành: 4xx thì bạn ngủ tiếp, 5xx thì bạn dậy sửa. Trả sai mã ở đây nghĩa là hệ thống cảnh báo của bạn thành vô dụng.

⚠️ Allow trên 405 không phải "cho đẹp" — RFC bắt buộc

RFC 9110 §15.5.6 viết nguyên văn: "The origin server MUST generate an Allow header field in a 405 response containing a list of the target resource's currently supported methods." Chữ MUST trong RFC là bắt buộc tuyệt đối. Lý do rất thực dụng: client nhận 405 mà không có Allow thì không biết phải thử lại bằng method nào — bạn vừa nói "sai rồi" mà không nói "vậy phải làm sao".

6. Header Content-Type: cái nhãn dán trên gói hàng

Bạn đã gõ 'Content-Type': 'application/json; charset=utf-8' vài lần mà chưa hỏi vì sao. Thử tháo nó ra xem sao — gửi đúng JSON nhưng dán nhãn text/plain:

bash — mở trình duyệt, dán vào thanh địa chỉ 
http://localhost:3337/courses

Chrome/Safari sẽ hiển thị JSON có cấu trúc, gập mở được. Bây giờ sửa route GET /courses đổi application/json thành text/plain, chạy lại và mở lại — chỉ còn một dòng chữ trơ trọi.

Body không hề đổi một byte nào. Chỉ cái nhãn đổi. Và đó là toàn bộ ý nghĩa của Content-Type: HTTP chuyển byte, nó không biết byte đó là gì; cái nhãn mới nói cho bên nhận biết phải hiểu đống byte ấy thế nào.

🚨 Vì sao dán nhãn sai là chuyện bảo mật, không chỉ chuyện thẩm mỹ

Giả sử API của bạn trả nội dung do người dùng nhập, mà bạn dán nhãn text/html. Trình duyệt sẽ thực thi phần <script> trong đó — kẻ tấn công vừa chạy được code trên trang của bạn (XSS). Cùng một chuỗi byte: dán nhãn application/json thì vô hại, dán nhãn text/html thì thành lỗ hổng. Bài 29 sẽ quay lại đề tài này; giờ chỉ cần khắc vào đầu: nhãn là một quyết định bảo mật.

  • Thấy tận mắt body 5MB về thành ~83 khúc, và hiểu vì sao không được giả định "nó về một lần"
  • Chứng kiến một request rác giết cả tiến trình — và biết vì sao Nest cần exception filter
  • Chọn đúng 200 / 201 / 400 / 404 / 405 và biết ranh giới 4xx (bạn sai) vs 5xx (tôi sai)
  • Hiểu Content-Type là một quyết định bảo mật, không phải trang trí

7. Câu hỏi tư duy (bắc cầu sang Bài 03)

Ở phần 3, khi bạn gửi body 5MB, handler đứng ở for await đợi từng khúc về. Trong lúc đợi đó — server có phục vụ được người khác không?

Thử nghĩ kỹ, vì hai câu trả lời đều nghe hợp lý. "Không": JavaScript chỉ có một luồng, nó đang mắc kẹt trong vòng lặp thì làm sao chạy việc khác. "Có": nếu mỗi upload lớn đều làm đứng cả server thì Node đã không ai dùng để làm backend.

Cả hai đều đúng một nửa, và chỗ chúng gặp nhau chính là thứ khiến Node tồn tại. Nó cũng giải thích luôn một câu đối lập mà bạn sẽ nghe suốt: "Node nhanh vì bất đồng bộ" và "Node chậm, đừng dùng cho việc nặng" — cả hai câu đều đúng, tuỳ vào bạn đang chờ I/O hay đang tính toán. Bài 03 mổ xẻ event loop để bạn nói được chính xác cái nào là cái nào.
