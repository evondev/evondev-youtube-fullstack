Module 2 · Bài 07

Exception filter: vì sao lỗi API phải có "hình dạng" cố định

API của bạn đang trả lỗi bằng hai khuôn khác nhau — và sắp có khuôn thứ ba. Bài này gom tất cả về một.

⏱ ~40 phút · 🎯 Sản phẩm: mọi lỗi — 400, 404, 500, cả lỗi bạn không lường trước — đều trả về cùng một hình dạng JSON, và không rò rỉ chi tiết nội bộ ra ngoài.

🌉 Bắc cầu từ Bài 06

Cuối Bài 06 tôi chỉ ra: lỗi validation trả message là mảng, còn lỗi 404 trả message là chuỗi. Cùng một API, hai khuôn.

Nghe như chuyện nhỏ. Nhưng hãy đứng ở phía người gọi API: họ phải viết Array.isArray(res.message) ? ... : ... ở mọi chỗ hiển thị lỗi. Và đó mới là hai khuôn — lát nữa bạn sẽ thấy khuôn thứ ba xuất hiện, thứ mà không ai chuẩn bị trước được.

1. Tự nhìn thấy vấn đề trước đã

Bật API rồi gọi hai lỗi khác nhau:

bash 
curl -s http://localhost:3333/courses/99
curl -s -X POST http://localhost:3333/courses \
  -H 'Content-Type: application/json' -d '{"title":"ab"}'
output THẬT — để ý trường message 
# 404 — message là CHUỖI
{"message":"Course with id=99 not found","error":"Not Found","statusCode":404}

# 400 — message là MẢNG
{"message":["level must be beginner or advanced", ...],"error":"Bad Request","statusCode":400}
💡 Vì sao "hình dạng lỗi" là một phần của HỢP ĐỒNG API

Client không đọc tài liệu để biết lỗi trông thế nào — họ viết code một lần rồi tin rằng mọi lỗi đều giống nhau. Mỗi khuôn lỗi khác nhau là một nhánh if nữa trong code của họ, và là một chỗ nữa để hỏng. Với API bạn giao cho khách freelance, đây là thứ họ chửi bạn sau khi đã ký hợp đồng.

2. Khuôn thứ ba: lỗi bạn không hề lường trước

Hai khuôn trên ít ra còn do bạn chủ động ném ra. Giờ xem cái bạn không chủ động.

🛑 ĐỌC TRƯỚC KHI DÁN — vị trí đặt route quyết định nó có chạy hay không

Nest khớp route theo thứ tự khai báo, không theo độ cụ thể. Nếu bạn dán @Get('boom') xuống cuối class (theo thói quen), thì @Get(':id') ở trên sẽ nuốt mất nó: "boom" bị nhận làm id, ParseIntPipe thấy không phải số và trả:

triệu chứng khi đặt SAI chỗ 
{"message":"Validation failed (numeric string is expected)",
 "error":"Bad Request","statusCode":400}

Hàm boom() lúc đó chưa chạy một lần nào — và không có lỗi nào báo cho bạn biết route đã bị che. Quy tắc: route cụ thể luôn khai TRƯỚC route có tham số động. Dán theo đúng khung dưới đây để khỏi sai.

elearning-api/src/courses/courses.controller.ts — chèn vào GIỮA hai route sẵn có 
  @Get()
  findAll(@Query('level') level?: string): Course[] {
    return this.coursesService.findAll(level);
  }

  // ┌──────────────── CHÈN VÀO ĐÂY ────────────────┐
  // TẠM THỜI: để thấy lỗi không lường trước trông thế nào. Xoá sau khi thử.
  @Get('boom')
  boom(): never {
    throw new Error('Kết nối Postgres thất bại: password=SuperSecret123');
  }
  // └──────────────────────────────────────────────┘

  @Get(':id')                    // ← 'boom' PHẢI nằm trên dòng này
  findOne(@Param('id', ParseIntPipe) id: number): Course {
    return this.coursesService.findOne(id);
  }
🔎 Cách tự kiểm mà không cần đoán

Bảng route lúc khởi động in đúng thứ tự Nest sẽ khớp. Nếu thấy Mapped {/courses/:id, GET} đứng trên Mapped {/courses/boom, GET} thì bạn đã đặt sai — nhìn bảng là biết, khỏi cần gọi thử.

bash 
curl -s http://localhost:3333/courses/boom
output THẬT (chưa có filter) 
{"statusCode":500,"message":"Internal server error"}

Khuôn thứ ba: không có trường error. Ba khuôn cho ba loại lỗi, trong cùng một API mà bạn mới viết được hai ngày.

🔎 Tin tốt giấu trong đây

Bạn vừa ném một Error thường — đúng thứ đã giết cả tiến trình ở Bài 04. Lần này server vẫn sống, client vẫn có câu trả lời. Nest đã bọc sẵn một lớp bắt lỗi quanh mọi handler. Bài này là học cách thay lớp mặc định đó bằng lớp của bạn.

3. Viết filter của riêng bạn

Tạo thư mục và file:

bash 
mkdir -p src/common/filters
elearning-api/src/common/filters/all-exceptions.filter.ts 
import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpException,
  HttpStatus,
  Logger,
} from '@nestjs/common';
import type { Request, Response } from 'express';

// Hình dạng lỗi DUY NHẤT của toàn bộ API. Frontend chỉ cần học đúng cái này.
interface ErrorBody {
  statusCode: number;
  error: string;
  messages: string[];
  path: string;
  timestamp: string;
}

// @Catch() để trống = bắt MỌI thứ ném ra, kể cả Error thường.
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  // Nest gọi hàm này mỗi khi có exception lọt ra khỏi handler.
  //   exception = thứ vừa bị ném ra. Kiểu `unknown` vì ta KHÔNG biết trước
  //               nó là gì — HttpException, Error, thậm chí một chuỗi.
  //   host      = "hộp đựng ngữ cảnh". Filter dùng lại được cho cả HTTP lẫn
  //               WebSocket/gRPC, nên Nest không đưa thẳng req/res mà đưa host.
  catch(exception: unknown, host: ArgumentsHost) {
    // Nói với host: "ngữ cảnh này là HTTP" -> giờ mới lấy được req/res.
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();   // để ta tự ghi response
    const request = ctx.getRequest<Request>();     // để đọc method + url

    // Phân đôi thế giới lỗi thành 2 loại. Đây là quyết định quan trọng nhất file này:
    //   - HttpException = lỗi CÓ CHỦ Ý (ta ném, hoặc pipe/Nest ném) -> nói thật cho client.
    //   - còn lại       = TAI NẠN ngoài dự tính -> giấu chi tiết, chỉ ghi log.
    const isHttpException = exception instanceof HttpException;

    // Lỗi có chủ ý thì tự nó mang sẵn status; tai nạn thì mặc định 500.
    const statusCode = isHttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    // messages: LUÔN là mảng chuỗi (kể cả 1 phần tử) -> client hết phải đoán kiểu.
    // error   : nhãn ngắn gọn, ví dụ 'Not Found' / 'Bad Request'.
    let messages: string[];
    let error: string;

    if (isHttpException) {
      // getResponse() trả về phần "ruột" mà người ném đã gắn vào exception.
      // Xui một nỗi: nó có HAI hình dạng khác nhau (xem giải thích ngay dưới).
      const payload = exception.getResponse();

      if (typeof payload === 'string') {
        // Dạng 1 — chuỗi trần: throw new NotFoundException('Course not found')
        messages = [payload];
        error = exception.name;
      } else {
        // Dạng 2 — object: ValidationPipe ném ra { message: [...], error: '...' }
        // Phải ép kiểu vì getResponse() khai là `string | object` — mà `object`
        // thì TypeScript không cho đọc .message, ta phải nói rõ mình mong gì.
        const body = payload as { message?: string | string[]; error?: string };

        // message có thể là mảng (validation, nhiều lỗi) hoặc chuỗi (một lỗi).
        // Bọc lại cho về mảng hết.
        messages = Array.isArray(body.message)
          ? body.message
          : [body.message ?? exception.message];

        // ?? = "nếu bên trái null/undefined thì lấy bên phải".
        error = body.error ?? exception.name;
      }
    } else {
      // TAI NẠN: tuyệt đối không kể chi tiết ra ngoài (xem phần 5).
      messages = ['Internal server error'];
      error = 'Internal Server Error';

      // Nhưng ghi log ĐẦY ĐỦ cho mình, kèm stack để còn debug.
      this.logger.error(
        `${request.method} ${request.url}`,
        exception instanceof Error ? exception.stack : String(exception),
      );
    }

    // Dựng body theo đúng khuôn đã khai ở trên, rồi TỰ TAY gửi đi.
    // Tới đây ta thay Nest làm việc trả response, nên phải gọi .status().json().
    const body: ErrorBody = {
      statusCode,
      error,
      messages,
      path: request.url,
      timestamp: new Date().toISOString(),
    };

    response.status(statusCode).json(body);
  }
}
💡 Ba thứ lạ trong đoạn trên — giải thích cho rõ

1. ArgumentsHost — vì sao không đưa thẳng req, res?
Vì Nest không chỉ chạy HTTP. Cùng một ứng dụng có thể phục vụ HTTP, WebSocket (Bài về realtime), hoặc gRPC — mỗi loại có "request/response" hình dạng khác nhau. Nên Nest đưa bạn cái hộp chung, rồi bạn mở đúng ngăn mình cần: host.switchToHttp() → ngăn HTTP, host.switchToWs() → ngăn WebSocket. Nhờ vậy filter viết một lần dùng được nhiều nơi.

2. getResponse<Response>() — cặp ngoặc nhọn để làm gì?
Nest không biết bạn chạy trên Express hay Fastify nên nó khai kiểu trả về rất chung. <Response> là bạn nói: "tôi biết đây là Response của Express" — nhờ đó editor mới gợi ý được .status(), .json(). Đây cũng là lý do phải import type { Request, Response } from 'express' ở đầu file.

3. Vì sao getResponse() có HAI hình dạng?
Vì hai người khác nhau ném ra, theo hai cách khác nhau — bạn tự kiểm chứng được:

cùng là HttpException, nhưng ruột khác nhau 
// Bạn ném ở Bài 05 — truyền một CHUỖI:
throw new NotFoundException('Course with id=99 not found');
   // -> getResponse() cho ra: 'Course with id=99 not found'   (chuỗi trần)

// ValidationPipe ném ở Bài 06 — nó cần chứa NHIỀU lỗi nên dùng OBJECT:
   // -> getResponse() cho ra: { message: ['title must...', 'price must...'],
   //                            error: 'Bad Request', statusCode: 400 }

Đó chính là nguồn gốc của "lúc là chuỗi, lúc là mảng" mà bạn thấy ở phần 1. Nhánh if (typeof payload === 'string') tồn tại đúng để gom hai thứ đó về một. Filter này không sửa được gốc rễ — nó chỉ dựng một bức tường trước khi lỗi ra tới client.

Bật nó lên trong src/main.ts:

elearning-api/src/main.ts — thêm 2 dòng 
import { AllExceptionsFilter } from './common/filters/all-exceptions.filter';  // ← THÊM

// ... bên trong bootstrap(), đặt trước app.listen():
app.useGlobalFilters(new AllExceptionsFilter());   // ← THÊM

4. Chạy lại — giờ mọi lỗi cùng một khuôn

bash — 5 loại lỗi khác nhau 
curl -s http://localhost:3333/courses/99          # 404 do ta ném
curl -s http://localhost:3333/courses/abc         # 400 do pipe
curl -s http://localhost:3333/khong-co-route      # 404 do Nest
curl -s http://localhost:3333/courses/boom        # 500 không lường trước
curl -s -X POST http://localhost:3333/courses \
  -H 'Content-Type: application/json' -d '{"title":"ab","level":"x","price":-5}'
output THẬT (đã verify — Nest 11) 
{"statusCode":404,"error":"Not Found",
 "messages":["Course with id=99 not found"],
 "path":"/courses/99","timestamp":"2026-08-26T16:15:21.054Z"}

{"statusCode":400,"error":"Bad Request",
 "messages":["Validation failed (numeric string is expected)"],
 "path":"/courses/abc", ...}

{"statusCode":404,"error":"Not Found",
 "messages":["Cannot GET /khong-co-route"],
 "path":"/khong-co-route", ...}

{"statusCode":500,"error":"Internal Server Error",
 "messages":["Internal server error"],
 "path":"/courses/boom", ...}

{"statusCode":400,"error":"Bad Request",
 "messages":["title must be at least 3 characters",
              "level must be beginner or advanced",
              "price must not be negative"],
 "path":"/courses", ...}

Năm nguồn lỗi hoàn toàn khác nhau — bạn ném, pipe ném, Nest ném, tai nạn — cùng đúng một khuôn. Frontend viết một hàm hiển thị lỗi, dùng cho cả API.

🔎 Vì sao đổi message thành messages

Số nhiều là lời hứa về kiểu dữ liệu: nó luôn là mảng, kể cả khi chỉ có một phần tử. Client viết messages.map(...) một lần, không bao giờ phải kiểm tra Array.isArray nữa. Đặt tên đúng số ít/số nhiều là cách rẻ nhất để một API tự mô tả chính nó.

5. Phần quan trọng nhất: đừng nói cho kẻ tấn công biết

Nhớ lại lỗi ta cố tình ném: 'Kết nối Postgres thất bại: password=SuperSecret123'. Kiểm xem client có thấy nó không:

bash 
curl -s http://localhost:3333/courses/boom | grep SuperSecret && echo "LỘ" || echo "AN TOÀN"
kết quả THẬT 
AN TOÀN

Nhưng nhìn sang terminal chạy server:

log server — THẬT 
ERROR [AllExceptionsFilter] GET /courses/boom
Error: Kết nối Postgres thất bại: password=SuperSecret123
    at CoursesController.boom (.../courses.controller.ts:29:11)
    at ...
🚨 Đây là ranh giới sống còn: log cho MÌNH, response cho NGƯỜI LẠ

Thông báo lỗi mặc định của thư viện thường chứa thứ cực kỳ hữu ích cho kẻ tấn công: tên bảng, tên cột, đường dẫn file trên server, phiên bản thư viện, đôi khi cả chuỗi kết nối. Đó là bản đồ hệ thống của bạn, trao tận tay miễn phí.

Quy tắc: lỗi 5xx không bao giờ được kể chi tiết ra ngoài. Lỗi 4xx thì ngược lại — phải nói rõ, vì đó là lỗi của client và họ cần biết để sửa. Filter ở trên làm đúng như vậy: HttpException giữ nguyên message, còn lại nuốt hết và chỉ ghi vào log.

Xoá route boom đi trước khi sang bài sau — nó chỉ để thí nghiệm.

6. Câu hỏi tư duy (bắc cầu sang Bài 08)

Trong filter bạn vừa viết có một quyết định bị giấu kín: lúc nào thì được phép trả chi tiết lỗi ra ngoài? Hiện tại câu trả lời là "không bao giờ". Nhưng khi bạn đang chạy máy local và tự debug, giấu chi tiết chính mình lại là phiền toái.

Vậy code phải biết nó đang chạy ở đâu — máy bạn hay production. Câu hỏi: thông tin đó đến từ đâu, và ai đảm bảo nó đúng? Nếu ai đó deploy lên production mà quên khai báo, code sẽ nghĩ mình đang ở đâu?
