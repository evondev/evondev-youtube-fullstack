Module 2 · Bài 06

DTO + ValidationPipe: chặn dữ liệu bẩn ngay ở biên

Thêm POST /courses vào e-learning — và dựng hàng rào để nghiệp vụ bên trong không bao giờ phải hỏi "cái này có đáng tin không".

⏱ ~40 phút · 🎯 Sản phẩm: tạo được khoá học mới; dữ liệu sai bị chặn bằng 400 kèm danh sách lỗi cụ thể; trường lạ bị đá ra.

🌉 Bắc cầu từ Bài 05

Cuối Bài 05 tôi hỏi: client gửi { "title": "abc", "price": "rất rẻ" } — ai chặn nó lại? ParseIntPipe chỉ lo được một tham số trên đường dẫn, còn đây là cả một object trong body.

Và câu nặng hơn: nếu không chặn thì phát hiện ra ở giai đoạn nào? Câu trả lời thật: rất muộn — lúc tính tiền sai, lúc trang hiển thị NaN đ, hoặc lúc database từ chối và làm sập một luồng nghiệp vụ đang chạy dở. Càng xa biên hệ thống, càng đắt. Bài này dựng cái biên đó.

1. Vì sao TypeScript không cứu được bạn ở đây

Ở Bài 05 controller viết @Body() dto: CreateCourseDto, kiểu rõ ràng. Phản xạ tự nhiên: "có TypeScript rồi, sai kiểu là nó báo". Sai.

sự thật cần khắc cốt 
TypeScript kiem tra luc  BIEN DICH  (tren may ban)
Du lieu ban lam den luc  CHAY THAT  (tren server)

-> Luc request toi noi, TypeScript DA BIEN MAT khoi file .js
-> Khong con ai kiem tra gi ca

Đây là điểm khác biệt lớn nhất khi chuyển từ frontend sang backend. Ở frontend, dữ liệu thường do chính code bạn tạo ra. Ở backend, dữ liệu đến từ người lạ — và họ gửi bất cứ thứ gì, kể cả thứ bạn không tưởng tượng nổi.

Nên ta cần một thứ kiểm tra lúc chạy. Đó là việc của DTO (Data Transfer Object — bản mô tả dữ liệu được phép đi vào) cộng với ValidationPipe.

2. Cài hai gói cần thiết

phiên bản THẬT đã cài & verify trên máy bạn

🔎 Hai gói này làm hai việc khác nhau

class-transformer biến cục JSON thô thành một thể hiện của class DTO. class-validator đọc các decorator trên class đó rồi kiểm tra. Phải có bước một thì bước hai mới có class để soi — đó là lý do luôn cài cặp, và cũng là lý do DTO phải là class, không được là interface: interface bốc hơi sau khi biên dịch, không mang theo decorator nào cả.

3. Viết DTO

Tạo src/courses/dto/create-course.dto.ts:

bash 
mkdir -p src/courses/dto
elearning-api/src/courses/dto/create-course.dto.ts 
import { IsIn, IsInt, IsString, Min, MinLength } from 'class-validator';

// DTO = hình dạng dữ liệu ĐƯỢC PHÉP đi vào hệ thống.
// Đây là class chứ không phải interface — vì decorator cần tồn tại lúc chạy.
export class CreateCourseDto {
  @IsString({ message: 'title phải là chuỗi' })
  @MinLength(3, { message: 'title phải từ 3 ký tự' })
  title: string;

  @IsIn(['co-ban', 'nang-cao'], { message: 'level chỉ nhận co-ban hoặc nang-cao' })
  level: 'co-ban' | 'nang-cao';

  @IsInt({ message: 'price phải là số nguyên' })
  @Min(0, { message: 'price không được âm' })
  price: number;
}
💡 Vì sao nên tự viết message tiếng Việt

Bỏ trống thì class-validator sinh câu mặc định tiếng Anh kiểu "title must be longer than or equal to 3 characters" — đúng nhưng lộ tên trường nội bộ và không dùng thẳng cho người dùng cuối được. Tự viết thì frontend hiển thị luôn chuỗi bạn trả về, không phải dịch lại ở hai nơi. Với API sẽ giao cho khách freelance, đây là chi tiết thấy ngay sự khác biệt giữa "chạy được" và "làm cho tử tế".

4. Bật ValidationPipe cho toàn ứng dụng

Sửa src/main.ts:

elearning-api/src/main.ts 
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Bật một lần ở đây = áp cho MỌI route, kể cả route viết sau này.
  app.useGlobalPipes(
    new ValidationPipe({
      // Cắt bỏ mọi trường KHÔNG khai báo trong DTO.
      whitelist: true,
      // Có trường lạ thì báo lỗi luôn thay vì im lặng cắt bỏ.
      forbidNonWhitelisted: true,
      // Biến JSON thô thành thể hiện của class DTO (cần cho validator).
      transform: true,
    }),
  );

  await app.listen(process.env.PORT ?? 3333);
}
bootstrap();

5. Thêm POST /courses

Thêm hàm create vào src/courses/courses.service.ts:

elearning-api/src/courses/courses.service.ts — thêm vào class 
// nhớ import ở đầu file:
// import { CreateCourseDto } from './dto/create-course.dto';

// Đặt cạnh mảng courses, trong class:
private idKeTiep = 3;

create(dto: CreateCourseDto): Course {
  // Tới được đây thì dto CHẮC CHẮN đã sạch — pipe đã lọc trước rồi.
  const course: Course = { id: this.idKeTiep++, ...dto };
  this.courses.push(course);

  return course;
}

Rồi thêm route vào src/courses/courses.controller.ts:

elearning-api/src/courses/courses.controller.ts 
// Bổ sung Body, Post vào dòng import @nestjs/common:
import { Body, Controller, Get, Param, ParseIntPipe, Post, Query } from '@nestjs/common';
import { CreateCourseDto } from './dto/create-course.dto';

// Thêm vào cuối class:
@Post()
create(@Body() dto: CreateCourseDto): Course {
  return this.coursesService.create(dto);
}
🔎 CreateCourseDto import thường, không phải import type

Khác với Course ở Bài 05. Vì Course là interface — biến mất sau khi biên dịch. Còn CreateCourseDto là class, phải còn tồn tại lúc chạy để Nest đọc decorator trên nó. Dùng import type ở đây là validation im lặng không chạy — bug rất khó tìm vì không có lỗi nào cả, chỉ là dữ liệu bẩn lọt qua.

💡 Ca số 2 — vì sao "báo hết một lượt" là quyết định thiết kế tốt

message là một mảng, không phải chuỗi. Client sai 3 trường thì nhận đủ 3 lỗi trong một lần gọi. Nếu chỉ báo lỗi đầu tiên, người dùng phải sửa–gửi–sửa–gửi ba vòng mới qua được form. Frontend cũng chỉ cần một lần gọi để tô đỏ đủ 3 ô. Đây là thứ phân biệt API dễ chịu với API hành người dùng — và bạn có nó miễn phí.

🚨 Ca số 4 quan trọng hơn nó trông — đây là lỗ hổng mass assignment

Client gửi kèm isAdmin: true. Không có whitelist, dòng { id, ...dto } trong service sẽ bê nguyên trường đó vào object và lưu lại. Đổi isAdmin thành role, price: 0, hay isPaid: true — bạn thấy ngay mức độ nghiêm trọng: người dùng tự nâng quyền cho mình, hoặc tự cho mình khoá học miễn phí.

Đây là lỗ hổng đã hạ nhiều hệ thống thật (GitHub từng dính năm 2012). Cách chặn đúng là danh sách trắng: chỉ nhận đúng những trường đã khai báo, mọi thứ khác đá ra — chính là whitelist: true + forbidNonWhitelisted: true bạn vừa bật. Ghi nhớ: đừng liệt kê thứ bị cấm (danh sách đen), hãy liệt kê thứ được phép.

7. Bức tranh: dữ liệu đi qua mấy lớp trước khi tới nghiệp vụ

vòng đời một POST /courses 
Client gui JSON tho
      |
      v
[ Nest doc body, parse JSON ]        <- Bai 02 ban tu viet tay
      |
      v
[ class-transformer ]                 <- JSON tho -> the hien CreateCourseDto
      |
      v
[ ValidationPipe + class-validator ]  <- soi decorator
      |            |
      |            +--- sai -> nem BadRequestException -> 400 + danh sach loi
      v                        (nghiep vu KHONG he chay)
[ CoursesController.create ]
      |
      v
[ CoursesService.create ]             <- toi day du lieu CHAC CHAN sach
      |
      v
   201 Created
💡 Giá trị thật nằm ở dòng "tới đây dữ liệu chắc chắn sạch"

Không có lớp này, mỗi hàm nghiệp vụ đều phải tự hỏi "cái này có đáng tin không" và tự kiểm lại — code ngập trong if (!title) ..., mà vẫn sót. Có lớp này, việc kiểm tra dồn về đúng một chỗ, ở biên, và toàn bộ phần trong được viết với giả định dữ liệu sạch. Đây chính là thứ Bài 02 bạn phải tự tay làm cho từng route và vẫn sót ca.

8. Câu hỏi tư duy (bắc cầu sang Bài 07)

Để ý hình dạng lỗi validation: { message: [...], error: "Bad Request", statusCode: 400 }. Còn lỗi 404 ở Bài 05: { message: "...", error: "Not Found", statusCode: 404 } — message lúc là mảng, lúc là chuỗi.

Bây giờ hình dung bạn là frontend gọi API này. Bạn viết code hiển thị lỗi thế nào khi cùng một trường lúc là mảng lúc là chuỗi? Và khi có thêm lỗi từ database, từ cổng thanh toán, từ chính bạn throw — ai đảm bảo tất cả đều cùng một hình dạng?

Câu hỏi nặng hơn: lúc lỗi xảy ra ở tầng sâu — ví dụ Postgres báo trùng khoá — thì client có nên nhìn thấy nguyên văn thông báo của Postgres không?
