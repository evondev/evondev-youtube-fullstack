Logging có cấu trúc + request-id: nhìn thấy hệ thống đang làm gì

Khách gọi điện báo lỗi. Log có hàng nghìn dòng. Bài này làm cho việc tìm ra dòng của họ mất 5 giây thay vì 45 phút.

⏱ ~40 phút · 🎯 Sản phẩm: mỗi request có một mã định danh riêng, đi theo nó qua mọi tầng — kể cả sau await — xuất hiện trong log và trong cả body lỗi trả về client.

🌉 Bắc cầu từ Bài 08

Cuối Bài 08 tôi đặt tình huống: production 200 request/giây, khách gọi điện báo lỗi, bạn mở log ra và thấy hàng nghìn dòng. Dòng nào là của người đó?

Và câu khó hơn: làm sao khâu nối các dòng log của cùng một request lại, khi chúng nằm rải rác giữa log của hàng trăm người khác — mà không phải truyền requestId qua từng hàm? Đó là phần hay nhất của bài này, và lời giải nằm ở một thứ có sẵn trong Node mà rất ít người biết.

1. Nhìn thấy vấn đề đã

Mở API và bắn vài request cùng lúc, rồi nhìn terminal chạy server:

bash 
seq 5 | xargs -P5 -I{} curl -s -o /dev/null http://localhost:3333/courses/99

Log hiện ra 5 dòng lỗi giống hệt nhau, không phân biệt được. Nếu chúng xen kẽ với log của request khác — mà production thì luôn như vậy — bạn không có cách nào biết dòng nào thuộc về ai.

💡 Vì sao đây là vấn đề của backend chứ không phải frontend

Ở frontend, mỗi tab trình duyệt là một thế giới riêng: bạn mở DevTools của đúng người dùng đó và thấy mọi thứ. Backend thì ngược lại — một tiến trình phục vụ tất cả mọi người cùng lúc (đúng sự thật từ Bài 01), nên mọi dòng log của mọi người đổ chung vào một chỗ. Không có cách nào tách ra trừ khi bạn tự đánh dấu từ đầu.

2. Ý tưởng: gắn thẻ cho mỗi request

điều ta muốn đạt được 
Request A tới  →  sinh id  a3f9...  →  mọi dòng log của nó mang [a3f9]
Request B tới  →  sinh id  7c21...  →  mọi dòng log của nó mang [7c21]

Log đổ chung một chỗ, nhưng lọc theo id là tách ra được:
    grep "a3f9" app.log   →  chỉ còn hành trình của request A

Nghe đơn giản. Cái khó nằm ở chỗ: service ở tầng sâu làm sao biết id của request đang chạy? Cách thô sơ là truyền nó xuống từng hàm:

cách thô sơ — đừng làm 
findAll(level?: string, requestId?: string)
findOne(id: number, requestId?: string)
create(dto: CreateCourseDto, requestId?: string)
// ... và MỌI hàm sau này, mãi mãi

Xấu, và lây lan: một hàm cần id thì cả chuỗi gọi phía trên nó đều phải nhận id để truyền xuống. Nghiệp vụ bị nhiễm bẩn bởi một thứ chẳng liên quan gì tới nghiệp vụ.

3. Lời giải: AsyncLocalStorage

Node có sẵn một thứ giải đúng bài toán này: AsyncLocalStorage trong module node:async_hooks. Hình dung nó là một ngăn kéo đi theo chuỗi thực thi: bạn bỏ gì vào lúc bắt đầu request, thì mọi hàm chạy sau đó — kể cả sau await — đều mở ngăn kéo ra lấy được, mà không ai phải truyền tay nhau.

💡 Vì sao nó làm được điều đó — nối thẳng vào Bài 03

Nhớ Bài 03: mỗi lần await, hàm của bạn nhả luồng ra và event loop chạy việc của người khác; lát sau mới quay lại. Vậy làm sao Node biết "quay lại chỗ nào của ai"? Vì nó vẫn theo dõi được chuỗi thực thi bất đồng bộ — đó chính là thứ async_hooks phơi ra cho bạn dùng. AsyncLocalStorage bám vào đúng cơ chế đó. Nói cách khác: bài này chỉ làm được vì event loop hoạt động như Bài 03 đã mô tả.

bash 
mkdir -p src/common/middleware
elearning-api/src/common/request-context.ts 
import { AsyncLocalStorage } from 'node:async_hooks';

interface RequestStore {
  requestId: string;
}

// AsyncLocalStorage: "ngăn kéo" đi theo suốt chuỗi async của MỘT request,
// mà không phải truyền requestId qua từng tham số hàm.
export const requestContext = new AsyncLocalStorage<RequestStore>();

export function getRequestId(): string | undefined {
  return requestContext.getStore()?.requestId;
}

4. Middleware sinh id

elearning-api/src/common/middleware/request-id.middleware.ts 
import { Injectable, NestMiddleware } from '@nestjs/common';
import { randomUUID } from 'node:crypto';
import type { NextFunction, Request, Response } from 'express';
import { requestContext } from '../request-context';

export const REQUEST_ID_HEADER = 'x-request-id';

@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(request: Request, response: Response, next: NextFunction) {
    // Tôn trọng id có sẵn (do gateway/client gửi), không có thì tự sinh.
    const incoming = request.header(REQUEST_ID_HEADER);
    const requestId = incoming && incoming.trim() !== '' ? incoming : randomUUID();

    // Trả lại cho client để họ đọc được khi đi báo lỗi.
    response.setHeader(REQUEST_ID_HEADER, requestId);

    // Mọi thứ chạy BÊN TRONG hàm này đều đọc được requestId, kể cả sau await.
    requestContext.run({ requestId }, () => next());
  }
}
🔎 Vì sao phải "tôn trọng id có sẵn"

Trong hệ thống thật, request của bạn thường đi qua nhiều chặng: trình duyệt → CDN → API gateway → API của bạn → dịch vụ khác. Nếu mỗi chặng tự sinh id riêng thì không nối lại được. Quy ước chung là: ai đó đã gắn id thì giữ nguyên, chưa ai gắn thì mình là người đầu tiên. Nhờ vậy một id duy nhất xâu chuỗi được toàn bộ hành trình qua mọi hệ thống — đây là nền của distributed tracing, thứ bạn sẽ gặp lại ở Bài về observability.

5. Logger tự dán id vào mỗi dòng

elearning-api/src/common/app-logger.service.ts 
import { ConsoleLogger, Injectable } from '@nestjs/common';
import { getRequestId } from './request-context';

// Kế thừa logger sẵn có của Nest, chỉ dán thêm requestId vào đầu mỗi dòng.
@Injectable()
export class AppLogger extends ConsoleLogger {
  private tag(message: unknown): string {
    const requestId = getRequestId();

    // Log lúc khởi động chưa thuộc request nào -> không có id, vẫn in bình thường.
    return requestId ? `[${requestId.slice(0, 8)}] ${String(message)}` : String(message);
  }

  log(message: unknown, ...rest: unknown[]) {
    super.log(this.tag(message), ...(rest as string[]));
  }

  error(message: unknown, ...rest: unknown[]) {
    super.error(this.tag(message), ...(rest as string[]));
  }

  warn(message: unknown, ...rest: unknown[]) {
    super.warn(this.tag(message), ...(rest as string[]));
  }
}

6. Nối tất cả lại

Đăng ký middleware cho mọi route trong app.module.ts:

elearning-api/src/app.module.ts 
import { MiddlewareConsumer, Module, NestModule } from '@nestjs/common';   // ← SỬA
import { RequestIdMiddleware } from './common/middleware/request-id.middleware';  // ← THÊM

// ... phần @Module({...}) giữ nguyên ...

export class AppModule implements NestModule {          // ← SỬA
  configure(consumer: MiddlewareConsumer) {
    // '*' = áp cho MỌI route, kể cả route thêm sau này.
    consumer.apply(RequestIdMiddleware).forRoutes('*');
  }
}

Bật logger trong main.ts:

elearning-api/src/main.ts 
import { AppLogger } from './common/app-logger.service';   // ← THÊM

// bufferLogs: giữ log khởi động lại, in ra bằng logger mới thay vì logger mặc định
const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useLogger(new AppLogger());

Và cho requestId vào body lỗi của Bài 07 — đây là mảnh ghép cuối:

elearning-api/src/common/filters/all-exceptions.filter.ts — 3 chỗ sửa

💡 Vòng tròn khép lại — đây là thứ bài này thật sự mua cho bạn

Khách gọi điện báo lỗi. Bạn hỏi "anh/chị đọc giúp tôi mã lỗi trên màn hình" — frontend hiển thị requestId lấy từ body lỗi. Họ đọc 457f82f2. Bạn gõ:

bash 
grep "457f82f2" app.log

Và ra đúng hành trình của người đó, tách khỏi hàng nghìn dòng của người khác. 45 phút mò kim đáy bể rút xuống 5 giây. Đây là khác biệt rất cụ thể giữa người từng vận hành hệ thống thật và người mới chỉ viết code chạy được — và là thứ khách freelance cảm nhận rõ nhất.

⚠️ Bước tiếp theo mà bài này CỐ Ý chưa làm

Log hiện vẫn là văn bản cho người đọc. Hệ thống thật thường log ra JSON một dòng ({"level":"error","requestId":"...","msg":"..."}) để máy lọc/gom được — thư viện phổ biến là pino. Tôi chưa đưa vào vì nó thêm một dependency và một tầng khái niệm, trong khi thứ đắt giá nhất là request-id thì bạn đã có rồi. Khi nào dự án cần gửi log lên dịch vụ tập trung, ta thay ConsoleLogger bằng pino — phần AsyncLocalStorage giữ nguyên không đổi một dòng.

8. Câu hỏi tư duy (bắc cầu sang Module 3)
