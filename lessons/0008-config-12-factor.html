🌉 Bắc cầu từ Bài 07

Cuối Bài 07 tôi hỏi: code làm sao biết nó đang chạy ở máy bạn hay production? Và nếu JWT_SECRET thiếu, bạn muốn hệ thống chạy tiếp với chuỗi rỗng hay từ chối khởi động?

Câu trả lời của bài này gói trong một chữ: fail fast. Cấu hình sai là loại lỗi chắc chắn sẽ gây hậu quả — chỉ là chưa biết lúc nào. Phát hiện nó lúc khởi động tốn của bạn 5 giây; phát hiện nó lúc có người đang thanh toán thì tốn hơn nhiều.

1. Vì sao cấu hình phải ra khỏi code

Nhìn lại main.ts hiện tại: process.env.PORT ?? 3333. Số 3333 nằm cứng trong code. Giờ hình dung API này chạy ở ba nơi:

Máy bạnStagingProduction
Cổng3333808080
Databaselocalhost:5433db-stagingdb nội bộ có mật khẩu
Khoá ký JWTgì cũng đượcchuỗi testbí mật thật
Cổng thanh toánsandboxsandboxtiền thật

Cùng một đoạn code, ba bộ giá trị. Nguyên tắc 12-factor III nói đúng một câu: lưu cấu hình trong môi trường, không trong code.

🚨 Phép thử để biết bạn đã tách đúng chưa

12-factor đưa ra một câu hỏi rất sắc: bạn có dám public repo này lên GitHub ngay bây giờ không? Nếu câu trả lời là "không, vì trong code có mật khẩu / khoá API" thì bạn chưa tách xong. Với Tuấn điều này rất thật: repo khoá học đang public, và Module 5 sẽ có khoá cổng thanh toán.

In ra một dòng = đã bị bỏ qua, an toàn. Không in gì = CHƯA an toàn, phải thêm .env vào .gitignore trước khi làm tiếp. Secret đã lên git công khai thì coi như lộ vĩnh viễn — xoá commit sau cũng vô ích, vì nó đã nằm trong lịch sử và trong bản clone của người khác.

3. Khai báo cấu hình mình cần — và ràng buộc của nó

Đây là chỗ hay nhất: ta dùng lại đúng class-validator của Bài 06, chỉ đổi đối tượng được kiểm — từ "body người dùng gửi lên" sang "biến môi trường".

bash 
mkdir -p src/config
elearning-api/src/config/env.validation.ts 
import { plainToInstance } from 'class-transformer';
import {
  IsEnum, IsInt, IsString, Max, Min, MinLength, validateSync,
} from 'class-validator';

export enum Environment {
  Development = 'development',
  Production = 'production',
  Test = 'test',
}

// Khai báo MỌI biến môi trường mà ứng dụng cần, kèm ràng buộc.
class EnvironmentVariables {
  @IsEnum(Environment, { message: 'NODE_ENV must be development | production | test' })
  NODE_ENV!: Environment;

  @IsInt({ message: 'PORT must be an integer' })
  @Min(1, { message: 'PORT must be >= 1' })
  @Max(65535, { message: 'PORT must be <= 65535' })
  PORT!: number;

  @IsString()
  @MinLength(16, { message: 'JWT_SECRET must be at least 16 characters' })
  JWT_SECRET!: string;
}

// Nest gọi hàm này MỘT LẦN lúc khởi động. Ném lỗi ở đây = app không lên.
export function validateEnv(config: Record<string, unknown>) {
  const parsed = plainToInstance(EnvironmentVariables, config, {
    enableImplicitConversion: true,   // '3333' -> 3333
  });

  const errors = validateSync(parsed, { skipMissingProperties: false });

  if (errors.length > 0) {
    const details = errors
      .flatMap((error) => Object.values(error.constraints ?? {}))
      .map((line) => `  - ${line}`)
      .join('\n');

    throw new Error(`\n❌ Cấu hình không hợp lệ:\n${details}\n`);
  }

  return parsed;
}
💡 Vì sao enableImplicitConversion lại cần ở đây

Biến môi trường luôn luôn là chuỗi — hệ điều hành không có khái niệm "số". Nên PORT tới tay bạn là "3333", và @IsInt sẽ trượt. enableImplicitConversion bảo class-transformer tự đổi theo kiểu đã khai. Nghe quen không? Đây đúng là chuyện ParseIntPipe ở Bài 06 — cùng một sự thật: mọi thứ từ bên ngoài vào đều là chuỗi cho tới khi bạn tự đổi nó.

4. Nối vào ứng dụng

elearning-api/src/app.module.ts 
import { ConfigModule } from '@nestjs/config';                // ← THÊM
import { validateEnv } from './config/env.validation';       // ← THÊM

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,          // khỏi phải import lại ở từng module
      validate: validateEnv,   // kiểm cấu hình NGAY lúc khởi động
    }),
    CoursesModule,
  ],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

Rồi đọc cấu hình đã được kiểm thay vì đọc thẳng process.env:

elearning-api/src/main.ts 
import { ConfigService } from '@nestjs/config';              // ← THÊM

// ... cuối bootstrap(), thay dòng app.listen cũ:
const config = app.get(ConfigService);
const port = config.get<number>('PORT', 3333);

await app.listen(port);

5. Thí nghiệm: phá cấu hình xem chuyện gì xảy ra

Chạy bình thường trước — phải lên được như thường:

bash 
npm run start

Giờ cố tình phá. Sửa .env thành:

elearning-api/.env — bản CỐ Ý SAI 
NODE_ENV=dev
PORT=khong-phai-so
JWT_SECRET=123
bash 
npm run start; echo "exit=$?"
output THẬT (đã verify) 
LOG [NestFactory] Starting Nest application...
ERROR [ExceptionHandler] Error:
❌ Cấu hình không hợp lệ:
  - NODE_ENV must be development | production | test
  - PORT must be <= 65535
  - PORT must be >= 1
  - PORT must be an integer
  - JWT_SECRET must be at least 16 characters

exit=1

Thử tiếp ca thiếu hẳn một biến — xoá dòng JWT_SECRET đi:

output THẬT 
❌ Cấu hình không hợp lệ:
  - JWT_SECRET must be at least 16 characters
  - JWT_SECRET must be a string

exit=1
💡 Ba điều đáng giá trong output đó
  • App KHÔNG lên. Không có cửa nào để một tiến trình cấu hình sai lọt vào production.
  • Liệt kê HẾT một lượt, không dừng ở lỗi đầu — sửa một lần là xong, y như chuyện messages là mảng ở Bài 06–07.
  • exit=1. Đây là chỗ quan trọng nhất mà ai cũng bỏ qua: Docker, Kubernetes, systemd, CI — tất cả đều nhìn mã thoát để biết tiến trình sống hay chết. Thoát bằng 1 nghĩa là cả dàn hạ tầng biết bản deploy này hỏng và tự động dừng rollout. Nếu ta chỉ console.log cảnh báo rồi chạy tiếp, hạ tầng tưởng mọi thứ ổn và cứ thế đưa bản hỏng ra cho người dùng.
🚨 Vì sao "chạy tiếp với giá trị mặc định" là lựa chọn tệ

Cách viết rất phổ biến: const secret = process.env.JWT_SECRET ?? '';. Trông vô hại, thực tế là thảm hoạ chờ sẵn — hệ thống lên bình thường, ký token bằng chuỗi rỗng, và ai cũng giả mạo được token. Không có lỗi nào báo, không có cảnh báo nào. Bạn chỉ biết khi có người đã vào được tài khoản người khác.

Đây chính là câu hỏi tôi để lại cuối Bài 07, và câu trả lời là: từ chối khởi động. Một hệ thống chết hẳn còn dễ chịu hơn nhiều so với một hệ thống chạy sai mà không ai biết.

Sửa .env về bản hợp lệ trước khi sang bài sau.

6. Việc nhỏ nhưng đừng bỏ: .env.example

.env không lên git — nên người tiếp theo clone repo về sẽ không biết cần những biến gì. Tạo một file mẫu, không chứa giá trị thật, và file này thì commit:

elearning-api/.env.example 
# Copy file này thành .env rồi điền giá trị thật
NODE_ENV=development
PORT=3333
# tối thiểu 16 ký tự — sinh bằng: openssl rand -hex 32
JWT_SECRET=
🔎 Với Tuấn thì "người tiếp theo" là ai?

Là chính bạn ở máy khác, là khách freelance nhận bàn giao, và là chính bạn ba tháng sau khi đã quên sạch. .env.example là tài liệu rẻ nhất bạn từng viết — và là thứ đầu tiên người ta mở khi nhận một repo lạ.

7. Câu hỏi tư duy (bắc cầu sang Bài 09)

Ở Bài 07 khi có lỗi 500, filter ghi vào log GET /courses/boom kèm stack trace. Giờ hình dung production lúc 9 giờ tối: 200 request mỗi giây, log đổ ra liên tục. Một khách hàng gọi điện: "tôi vừa thanh toán và nó báo lỗi".

Bạn mở log ra và thấy hàng nghìn dòng. Làm sao biết dòng nào là của người đó? Và giả sử tìm được dòng báo lỗi — làm sao biết những việc gì đã chạy trước đó trong cùng request ấy, giữa hàng nghìn dòng của những người khác đan xen vào?

Câu hỏi khó hơn: một request đi qua middleware → controller → service → gọi database, mỗi chỗ log một dòng. Làm sao khâu nối chúng lại mà không phải truyền một tham số requestId qua từng hàm?
