Module 2 · Bài 05

NestJS: Module – Controller – Service, và endpoint thật đầu tiên

Hết thời lab/. Từ bài này code bạn viết nằm trong src/ của API thật — và cuối bài, elearning-api có endpoint khoá học chạy được.

⏱ ~40 phút · 🎯 Sản phẩm: GET /courses · GET /courses?level= · GET /courses/:id — có lọc, có 404, có 400, không dòng nào bạn phải tự viết.

🌉 Bốn bài vừa rồi không phí — đây là lúc thu hoạch

Ở Bài 02 bạn tự tay làm 5 việc cho mỗi request: tách pathname khỏi query, so method, gom body từ stream, chọn status code, dán Content-Type. Mỗi route thêm vào là chép lại từng ấy việc.

NestJS làm đúng năm việc đó, tự động. Nhưng vì bạn đã tự viết tay một lần, bạn sẽ nhìn ra ngay nó đang làm hộ cái gì — chứ không phải học thuộc mấy cái decorator rồi cầu cho nó chạy. Đó là toàn bộ lý do Module 1 tồn tại.

1. Ba khái niệm, và vì sao phải tách ra ba

Nest bắt bạn chia code thành ba loại. Nghe như thủ tục rườm rà, nhưng mỗi cái trả lời một câu hỏi khác nhau:

ThứTrả lời câu hỏiTrong e-learning
Controller Request nào thì gọi hàm nào? Lấy dữ liệu ra khỏi HTTP. "GET /courses thì chạy gì"
Service Nghiệp vụ thật sự làm gì? Không biết gì về HTTP. "lọc khoá học theo trình độ"
Module Những thứ trên thuộc về nhóm nào, ai được dùng ai? "nhóm khoá học gồm controller + service này"
💡 Vì sao tách Service ra khỏi Controller — lý do thực dụng

Vì nghiệp vụ sống lâu hơn giao diện của nó. Cùng một việc "lọc khoá học" sau này sẽ được gọi từ: HTTP, một cron job nhắc học (Bài 38), một hàng đợi gửi mail (Bài 37), và test tự động (Bài 43). Nếu logic nằm trong controller, nó dính chặt vào request/response và chỉ dùng được qua HTTP. Tách ra service thì bốn chỗ kia gọi thẳng như một hàm bình thường.

Đây cũng là câu trả lời cho "sao không viết hết vào controller cho nhanh?" — nhanh hơn đúng lúc đầu, rồi trả giá ở lần thứ hai cần dùng lại.

2. Tạo nhóm khoá học

Tạo thư mục mới trong src/:

bash 
cd ~/Documents/youtube/fullstack/elearning-api
mkdir -p src/courses

File 1 — hình dạng dữ liệu. Tạo src/courses/course.interface.ts:

elearning-api/src/courses/course.interface.ts 
// Hình dạng của một khoá học. Dùng interface theo đúng convention của bạn.
export interface Course {
  id: number;
  title: string;
  level: 'beginner' | 'advanced';
  price: number;
}

File 2 — nghiệp vụ. Tạo src/courses/courses.service.ts:

elearning-api/src/courses/courses.service.ts 
import { Injectable, NotFoundException } from '@nestjs/common';
import { Course } from './course.interface';

// @Injectable() = "class này có thể được Nest tạo và tiêm vào chỗ khác".
@Injectable()
export class CoursesService {
  // Tạm để trong bộ nhớ. Module 3 sẽ thay bằng Postgres thật.
  private readonly courses: Course[] = [
    { id: 1, title: 'NestJS Fundamentals', level: 'beginner', price: 499000 },
    { id: 2, title: 'Postgres for Backend', level: 'advanced', price: 799000 },
  ];

  findAll(level?: string): Course[] {
    if (!level) return this.courses;

    return this.courses.filter((course) => course.level === level);
  }

  findOne(id: number): Course {
    const course = this.courses.find((item) => item.id === id);

    // Ném exception, KHÔNG tự tay writeHead(404). Nest lo phần còn lại.
    if (!course) throw new NotFoundException(`Course with id=${id} not found`);

    return course;
  }
}

Để ý: cả file này không có một chữ nào về HTTP. Không request, không response, không status code. Đó là dấu hiệu bạn tách đúng.

File 3 — cửa vào HTTP. Tạo src/courses/courses.controller.ts:

elearning-api/src/courses/courses.controller.ts 
import { Controller, Get, Param, ParseIntPipe, Query } from '@nestjs/common';
import { CoursesService } from './courses.service';
// Chú ý `import type` — bắt buộc, giải thích ở callout ngay dưới.
import type { Course } from './course.interface';

// Mọi route trong class này đều bắt đầu bằng /courses
@Controller('courses')
export class CoursesController {
  // Nest TỰ tạo CoursesService và đưa vào đây — ta không hề gọi `new`.
  constructor(private readonly coursesService: CoursesService) {}

  @Get()
  findAll(@Query('level') level?: string): Course[] {
    return this.coursesService.findAll(level);
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number): Course {
    return this.coursesService.findOne(id);
  }
}
⚠️ Bỏ chữ type đi là build gãy — tôi đã dính khi soạn bài này

Viết import { Course } như bình thường, chạy npx tsc --noEmit sẽ ra:

lỗi THẬT tôi gặp khi verify 
error TS1272: A type referenced in a decorated signature must be
imported with 'import type' ... when 'isolatedModules' and
'emitDecoratorMetadata' are enabled.

Vì sao: decorator của Nest cần TypeScript phát ra thông tin kiểu vào file JS lúc biên dịch. Với một interface — thứ biến mất hoàn toàn sau khi biên dịch — trình biên dịch không biết nên giữ hay bỏ dòng import. import type nói rõ: "đây chỉ là kiểu, xoá đi lúc build". Gặp TS1272 ở bất kỳ đâu trong Nest, cách sửa luôn là thêm chữ type.

File 4 — gom nhóm. Tạo src/courses/courses.module.ts:

elearning-api/src/courses/courses.module.ts 
import { Module } from '@nestjs/common';
import { CoursesController } from './courses.controller';
import { CoursesService } from './courses.service';

@Module({
  controllers: [CoursesController],
  // providers = những thứ Nest được phép tạo và tiêm vào trong nhóm này.
  providers: [CoursesService],
})
export class CoursesModule {}

Cuối cùng, khai báo nhóm mới với ứng dụng. Sửa src/app.module.ts:

elearning-api/src/app.module.ts — thêm 2 dòng 
import { Module } from '@nestjs/common';
import { AppController } from './app.controller';
import { AppService } from './app.service';
import { CoursesModule } from './courses/courses.module';   // <-- THEM

@Module({
  imports: [CoursesModule],                                    // <-- THEM
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

💡 Cái đáng giá nhất trong bảng trên là dòng cuối

Ở Bài 02, mỗi lần cần báo lỗi bạn phải nhớ tự tay ghi status và tự bịa hình dạng JSON — và bạn đã thấy hậu quả: quên một nhánh là client treo, ném lỗi là cả server chết (Bài 04).

Ở đây bạn chỉ throw. Nest bắt lấy, đổi thành response đúng chuẩn, và tiến trình vẫn sống. Đó chính là exception filter — thứ tôi hẹn từ Bài 02. Nó là lời giải cho đúng cái tai nạn bạn đã tự gây ra trong lab/.

5. Điều kỳ lạ: ta chưa hề gọi new CoursesService()

Nhìn lại controller: nó dùng this.coursesService, nhưng không chỗ nào tạo ra đối tượng đó. Chỉ khai báo trong constructor, thế là có.

Nest làm gì lúc khởi động 
1. Đọc @Module  →  thấy providers: [CoursesService]
2. Đọc constructor của CoursesController
   →  "nó cần một CoursesService"
3. Tạo MỘT thể hiện CoursesService, cất vào sổ
4. Tạo CoursesController, đưa thể hiện đó vào
5. Ai cần CoursesService nữa  →  đưa LẠI CÁI CŨ, không tạo mới

Cái này gọi là Dependency Injection: bạn khai báo mình cần gì, không tự đi lấy. Nest giữ một cuốn sổ các thứ nó biết tạo, và lắp vào đúng chỗ.

💡 Được gì so với việc tự new?
  • Mặc định chỉ có một thể hiện dùng chung cả ứng dụng. Quan trọng khi service giữ thứ đắt tiền như kết nối database — bạn không muốn mỗi request mở một kết nối mới.
  • Thay được lúc test. Vì controller không tự tạo service, lúc test bạn đưa cho nó một service giả — không cần database nào. Đó là Bài 43.
  • Đổi ruột không đổi vỏ. Hôm nay CoursesService đọc từ mảng trong bộ nhớ; Module 3 đổi sang Postgres. Controller không phải sửa một chữ — nó chỉ biết "có ai đó cho tôi danh sách khoá học".
⚠️ Lỗi DI kinh điển bạn chắc chắn sẽ gặp

Quên đưa service vào providers → Nest báo: Nest can't resolve dependencies of the CoursesController (?). Dấu ? chính là chỗ nó không tìm ra. Đọc được dấu hỏi nằm ở tham số thứ mấy là biết ngay thiếu cái gì — gần như luôn là quên khai báo trong providers, hoặc service nằm ở module khác mà module đó chưa exports.

6. Câu hỏi tư duy (bắc cầu sang Bài 06)

Dữ liệu khoá học đang nằm trong một mảng cứng giữa CoursesService. Rõ ràng là tạm. Nhưng trước khi thay bằng database, có một câu phải trả lời trước:

Giờ ta thêm POST /courses để tạo khoá học mới. Client gửi lên { "title": "abc", "price": "rất rẻ" } — price là chuỗi, không phải số. Ai chặn nó lại? ParseIntPipe chỉ lo được một tham số trên đường dẫn, còn đây là cả một object trong body.

Và câu hỏi nặng hơn: nếu không chặn, dữ liệu bẩn sẽ đi tới đâu — và bạn sẽ phát hiện ra nó ở giai đoạn nào? Lúc ghi vào database, lúc người dùng xem trang, hay lúc tính tiền?
