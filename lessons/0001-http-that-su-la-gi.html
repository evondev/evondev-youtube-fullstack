Module 1 · Bài 01

HTTP thực sự là gì — tự viết web server bằng node:http thuần

Không framework, không decorator. 20 dòng code để thấy backend không hề có ma thuật nào.

⏱ ~40 phút · 🎯 Mục tiêu: bạn tự gõ tay một HTTP request bằng nc và server trả lời; rồi bạn viết một server của riêng bạn mà curl nói chuyện được.

🌉 Bắc cầu từ cái bạn đã biết

Ở Next.js bạn viết await fetch('/api/courses') cả nghìn lần. Bạn biết rõ phía bạn làm gì: gọi hàm, chờ Promise, đọc .json(). Nhưng phía bên kia sợi dây — cái đang nghe và trả lời — với bạn nó vẫn là một hộp đen.

Bài này mở hộp đen đó ra. Câu chốt bạn cần mang theo suốt 56 bài còn lại: một request HTTP chỉ là một đoạn văn bản có quy tắc, và một web server chỉ là một hàm được gọi lại mỗi khi đoạn văn bản đó tới. Hết. Toàn bộ NestJS là các lớp tiện nghi bọc quanh đúng hai câu này.

Giải phẫu request (phần >) — nó luôn có đúng 3 phần:

PhầnTrong ví dụNghĩa là gì
Dòng đầu (request line)GET / HTTP/1.1Động từ + đường dẫn + phiên bản giao thức. Bắt buộc là dòng đầu tiên.
Các headerHost:, User-Agent:…Cặp Tên: giá trị, mỗi cặp một dòng. Đây là "phong bì" — thông tin về gói tin.
Dòng trốngdòng > rỗngQuan trọng nhất mà ai cũng bỏ qua: nó đánh dấu "hết header, phần sau là body".
Body (tuỳ chọn)không có với GETDữ liệu thật. POST mới thường có.

Response (phần <) có cấu trúc y hệt, chỉ khác dòng đầu: HTTP/1.1 200 OK — phiên bản + mã trạng thái + mô tả.

💡 Vì sao phải biết cái này (chứ không phải học thuộc cho vui)

Vì mọi bug mạng bạn sẽ gặp trong 5 năm tới đều nằm ở một trong 4 dòng trên. CORS hỏng? Thiếu header. Upload 413? Content-Length vượt giới hạn. Client treo? Body không bao giờ kết thúc. Webhook chạy 2 lần? Bên gửi không thấy response nên gửi lại. Khi bạn nhìn HTTP là văn bản đọc được, bạn debug bằng mắt; khi bạn nhìn nó là ma thuật, bạn debug bằng cách đoán.

Theo RFC 9112 §2.1 (đặc tả chính thức của HTTP/1.1), một message HTTP đúng là: start-line, rồi các header, rồi CRLF (ký tự xuống dòng kiểu Windows: \r\n), rồi body. Không hơn.

2. Thí nghiệm: tự tay gõ một HTTP request

Nếu HTTP chỉ là văn bản, ta phải gửi được nó mà không cần trình duyệt, không cần curl. nc (netcat, có sẵn trên macOS) là công cụ chỉ làm đúng một việc: mở kết nối TCP và đẩy chữ qua đó. Không hề biết HTTP là gì.

bash — tab 2 (API Bài 00 vẫn đang chạy ở tab 1) 
# printf gõ ra đúng văn bản của một request HTTP hợp lệ.
#   \r\n  = xuống dòng kiểu CRLF, đúng chuẩn RFC (dùng \n thôi là sai chuẩn)
#   Host  = header BẮT BUỘC của HTTP/1.1, thiếu là server trả 400
#   \r\n\r\n cuối = dòng trống báo "hết header"
# Rồi ống (|) đẩy nguyên đoạn chữ đó qua kết nối TCP tới cổng 3333.
printf 'GET / HTTP/1.1\r\nHost: localhost:3333\r\nConnection: close\r\n\r\n' | nc localhost 3333

Server trả lời bạn — dù bạn chưa hề dùng trình duyệt hay thư viện HTTP nào. Đây là toàn bộ "ma thuật" của web. Trình duyệt Chrome, hàm fetch(), Postman — tất cả chỉ là những cỗ máy gõ đoạn chữ này giúp bạn.

🔎 Thử nghịch cho hiểu sâu (30 giây)

Chạy lại lệnh trên nhưng xoá header Host đi. Bạn sẽ nhận 400 Bad Request. Vì sao? Vì một địa chỉ IP có thể phục vụ hàng trăm website (virtual host) — không có Host, server không biết bạn hỏi website nào. Đó là lý do header này bắt buộc từ HTTP/1.1.

3. Giờ tới lượt bạn: viết server không framework

Node có sẵn module http — không cần cài gì. Tạo thư mục lab/ trong project (đây là nơi sống của 4 bài "kiến thức nền", tách khỏi src/ của API thật):

mkdir -p lab
⚠️ VS Code sẽ gạch đỏ file trong lab/ — và đây là lỗi "đúng"

Vừa tạo file .mjs trong lab/ là ESLint kêu ngay: Parsing error: ... was not found by the project service. File của bạn không sai gì cả — node lab/01-http-tho.mjs vẫn chạy ngon.

Nguyên nhân: bộ ESLint mà Nest sinh ra dùng chế độ type-aware — nó bắt buộc mọi file phải nằm trong tsconfig.json để đọc được kiểu. Mà tsconfig.json chỉ gom file TypeScript trong src/, còn lab/ là JS thuần cố ý đứng ngoài (nó không build ra dist/, không lên production).

Cách sửa đúng: nói với ESLint là bỏ qua lab/, chứ không kéo lab/ vào tsconfig. Sửa elearning-api/eslint.config.mjs:

Tạo file lab/01-http-tho.mjs trong editor và dán nội dung sau:

elearning-api/lab/01-http-tho.mjs 
// Module http CÓ SẴN trong Node — không cần npm install.
// Tiền tố "node:" nói rõ đây là module lõi, không phải một gói npm trùng tên.
import { createServer } from 'node:http';

// createServer nhận MỘT hàm. Node gọi lại hàm này MỖI KHI có một request tới.
//   req = thứ client gửi lên (chỉ đọc)
//   res = cái ống để ta ghi câu trả lời ngược về
const server = createServer((req, res) => {
  // In ra terminal để thấy tận mắt: mỗi request = một lần hàm này chạy.
  console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);

  // Dòng đầu của response: mã trạng thái + các header gửi kèm.
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });

  // end() = ghi nốt phần body VÀ đóng response lại.
  // Không gọi end() thì client ngồi đợi tới già — ta sẽ thử ở phần 5.
  res.end('Xin chao tu server tu viet!\n');
});

// listen() = mở cổng VÀ giữ tiến trình sống. Đây là khác biệt lớn nhất so với
// một script thường: script chạy hết dòng cuối là thoát, còn server thì đứng đó chờ.
server.listen(3334, () => {
  console.log('Server dang nghe tai http://localhost:3334');
});

Nhìn sang tab 3 — terminal chạy server — bạn sẽ thấy dòng log hiện ra ngay khoảnh khắc bạn gọi. Gọi thêm lần nữa: thêm một dòng. Đó chính là "vòng đời" của backend: một tiến trình đứng yên, và mỗi request là một lần hàm của bạn được đánh thức.

💡 Khác biệt tư duy lớn nhất so với frontend

Component React chết đi sống lại liên tục — re-render, unmount, refresh trang là sạch trơn. Tiến trình server thì sống hàng tuần liền và phục vụ hàng triệu request bằng cùng một vùng nhớ. Hệ quả bạn phải khắc cốt ghi tâm: một biến bạn lỡ gán ở request của user A vẫn còn đó khi request của user B tới. Cả một lớp bug backend (rò rỉ dữ liệu giữa các user, memory leak, race condition) sinh ra từ đúng sự thật này.

4. So sánh: server của bạn vs NestJS

Đặt hai response cạnh nhau — cùng một câu chào, hai bộ header khác nhau:

HeaderServer của bạn (node:http)NestJS ở cổng 3333
X-Powered-Bykhông cóExpress — Nest chạy trên Express
Content-Lengthkhông có12
Transfer-Encodingchunkedkhông có
ETagkhông cóW/"c-Lve95..." — để cache
Date, Connectioncócó

Hai dòng Date và Connection bạn không hề viết mà vẫn có — Node tự thêm, vì RFC yêu cầu. Còn chunked xuất hiện vì lý do rất đời:

💡 Vì sao của bạn là chunked còn của Nest là Content-Length?

Khi writeHead chạy, Node chưa biết bạn sắp ghi bao nhiêu byte — bạn có thể ghi tiếp cả trăm lần trước khi end(). Không biết độ dài thì không khai Content-Length được, nên nó dùng Transfer-Encoding: chunked: gửi từng khúc, mỗi khúc kèm độ dài, khúc 0 báo hết. Chạy lại lệnh nc trỏ vào cổng 3334 bạn sẽ thấy tận mắt con số 1c (28 ở hệ 16 = độ dài câu chào) và số 0 kết thúc.

Express thì gom sẵn cả chuỗi rồi mới gửi nên đo được độ dài → khai Content-Length. Đánh đổi: chunked cho phép stream (bắt đầu trả lời trước khi biết kết quả dài bao nhiêu — chính là thứ làm nên hiệu ứng chữ chạy dần của ChatGPT), đổi lại client không biết trước còn bao lâu nữa nên không vẽ được thanh tiến trình.

5. Thí nghiệm bắt buộc: quên res.end()

Đây là lỗi backend kinh điển, và bạn phải thấy nó bằng mắt một lần thì mới nhớ đời. Ở tab 3, bấm Ctrl+C tắt server, sửa file: xoá dòng res.end(...) (hoặc comment lại), rồi chạy lại. Ở tab 2:

bash — tab 2 
# --max-time 3: tự bỏ cuộc sau 3 giây, để bạn khỏi ngồi đợi vô tận
curl -s --max-time 3 http://localhost:3334; echo "exit=$?"
kết quả THẬT (đã verify) 
exit=28   # 28 = Operation timeout. Không có lỗi, không có 500. Chỉ là im lặng.
🚨 Vì sao đây là loại bug đáng sợ nhất

Server không crash, không báo lỗi, log vẫn xanh — nó chỉ đơn giản là không bao giờ trả lời. Nhìn từ phía monitoring thì "mọi thứ bình thường", còn user thì thấy trang quay mãi. Tệ hơn: mỗi kết nối treo vẫn chiếm chỗ trong tiến trình; đủ nhiều thì server hết tài nguyên và chết cả cụm. Ghi nhớ luật: mọi nhánh code trong handler đều phải kết thúc bằng một response. Bài 12 sẽ cho thấy Nest tự động hoá luật này bằng exception filter ra sao — và vì sao vẫn có cách làm nó trượt.

Sửa lại res.end(...) như cũ trước khi làm bài tập nhé.

7. Câu hỏi tư duy (bắc cầu sang Bài 02)

Server bạn vừa viết trả lời y hệt nhau cho mọi request: GET / hay DELETE /users/9 cũng ra một câu chào và một mã 200. Rõ ràng là sai.

Vậy: khi client gửi POST kèm một cục JSON, cục JSON đó nằm ở đâu trong req? Thử console.log(req.body) xem — bạn sẽ nhận undefined. Vì sao Node không đưa sẵn body cho bạn, trong khi nó đã đưa sẵn req.method và req.url? Sự khác biệt giữa hai thứ đó nói lên điều gì về cách dữ liệu đi qua mạng?

Trả lời được câu này là bạn hiểu stream — và hiểu luôn vì sao mọi framework backend đều cần một thứ gọi là "body parser".
