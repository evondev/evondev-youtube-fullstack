Dựng sân tập: NestJS + Postgres + Redis

Một hệ thống backend chạy được trên máy bạn — nền móng cho cả 56 bài sau.

⏱ ~40 phút · 🎯 Mục tiêu: gõ 3 lệnh kiểm tra và cả 3 đều xanh — API trả lời, Postgres trả lời, Redis trả lời.

🌉 Bắc cầu từ cái bạn đã biết

Bạn đã quen npm run dev của Next.js: một tiến trình Node lắng nghe cổng 3000, bạn mở trình duyệt và thấy trang. Backend y hệt vậy — cũng là một tiến trình Node lắng nghe một cổng — chỉ khác ở chỗ nó trả về JSON thay vì HTML, và nó cần thêm hai người bạn đứng sau: một database (nơi dữ liệu sống sót khi tắt máy) và một cache (nơi dữ liệu chết nhanh nhưng đọc cực nhanh).

Bài này không dạy code. Bài này dựng cái sân để 56 bài sau có chỗ mà đá.

💡 Vì sao Node v22 mà không nâng lên v24?

Node LTS mới nhất hiện là v24, nhưng docs NestJS chỉ yêu cầu Node >= 20. v22 của bạn thoả. Nguyên tắc senior: đừng nâng version khi chưa có lý do. Mỗi lần nâng là một lần rủi ro; đổi lấy cái gì thì phải nói được. Ta sẽ nâng khi nào có thứ cụ thể cần tới v24.

1. Tạo project elearning-api

Mở Terminal. Đầu tiên vào đúng thư mục khoá học này, rồi để Nest CLI sinh bộ khung:

bash — tạo project 
# Vào thư mục workspace của khoá học (nơi chứa lessons/, MISSION.md...)
cd ~/Documents/fullstack

# Sinh bộ khung NestJS. Giải thích từng cờ:
#   --package-manager npm : dùng npm, khỏi bị CLI hỏi qua lại
#   --skip-git            : KHÔNG tạo git repo riêng bên trong project,
#                           vì ta muốn git quản lý cả workspace (bài học + code)
#   --strict              : bật TypeScript strict mode ngay từ đầu
nest new elearning-api --package-manager npm --skip-git --strict

Lệnh này mất ~1–2 phút (nó cài node_modules). Chạy xong bạn sẽ thấy:

output thật (đã verify trên máy bạn) 
🚀  Successfully created project elearning-api
👉  Get started with the following commands:

$ cd elearning-api
$ npm run start
🔎 Bộ khung vừa sinh ra có gì
  • src/main.ts — cửa vào. Chỗ tiến trình Node khởi động và mở cổng.
  • src/app.module.ts — gốc cây module. Nest lắp ráp toàn hệ thống từ đây.
  • src/app.controller.ts — nơi khai báo "URL nào thì gọi hàm nào".
  • src/app.service.ts — nơi chứa nghiệp vụ, tách khỏi HTTP.

Bốn file này là toàn bộ triết lý của Nest. Bài 08–10 sẽ mổ xẻ vì sao lại chia như vậy — giờ chỉ cần biết chúng tồn tại.

2. Đổi cổng 3000 → 3333 (bắt buộc với máy bạn)

🚨 Tôi đã thử và nó gãy trên máy bạn

Nest mặc định chạy cổng 3000. Nhưng máy bạn đang có một dev server Next.js chiếm cổng 3000 (tôi kiểm tra thấy tiến trình node PID 74939 đang giữ nó). Nếu để nguyên, bạn sẽ gặp đúng lỗi này:

lỗi thật tôi gặp khi verify 
Error: listen EADDRINUSE: address already in use :::3000
  code: 'EADDRINUSE',
  port: 3000

EADDRINUSE = "địa chỉ đang bị dùng". Một cổng chỉ được đúng một tiến trình lắng nghe. Đây là lỗi backend kinh điển — nhớ mặt nó luôn, bạn sẽ gặp lại nhiều.

Mở src/main.ts và sửa thành:

elearning-api/src/main.ts 
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  // Nest đọc AppModule, tự lắp ráp toàn bộ cây phụ thuộc, rồi trả về app đã sẵn sàng.
  const app = await NestFactory.create(AppModule);

  // 3333 thay vì 3000 vì cổng 3000 trên máy bạn đang bị Next.js giữ.
  // process.env.PORT được ưu tiên: khi deploy production, nhà cung cấp
  // (Railway/Fly/Heroku...) sẽ tự tiêm PORT vào — code không cần đổi. (12-factor)
  await app.listen(process.env.PORT ?? 3333);
}
bootstrap();

bash — terminal #2

curl -i http://localhost:3333

💡 Ba thứ đáng chú ý trong 5 dòng trên
  • 200 OK — status code. Máy đọc dòng này để biết thành công hay thất bại, chứ không đọc chữ.
  • X-Powered-By: Express — NestJS không tự viết HTTP server; nó chạy trên Express. Nest là lớp kiến trúc, không phải lớp mạng. Điểm này rất hay bị hỏi khi phỏng vấn.
  • Content-Type: text/html — nó đang trả HTML. API thật phải trả application/json. Bài 02 sẽ sửa.

4. Dựng Postgres + Redis bằng Docker

💡 Vì sao dùng Docker khi máy bạn ĐÃ có Postgres 18 qua Homebrew?

Ba lý do, theo thứ tự quan trọng:

  1. Giống production. Server thật của bạn sau này chạy Postgres trong container Linux. Bản Homebrew chạy trên macOS — khác OS, khác cách build. "Chạy được trên máy tôi" là câu nói khiến freelancer mất khách.
  2. Vứt đi được. Làm hỏng database? docker compose down -v rồi dựng lại trong 10 giây. Với Homebrew bạn phải đi dọn thủ công.
  3. Mỗi project một bộ. Bạn đang có sẵn 2 project khác dùng Postgres trên máy này. Docker cho mỗi project database riêng, version riêng, không giẫm chân nhau.

Đánh đổi: Docker tốn RAM và chậm hơn native một chút. Với dev thì không đáng kể. Bản Homebrew ta vẫn giữ — dùng lệnh psql của nó làm client để kết nối vào container.

Bước 4a. Mở Docker Desktop (bắt buộc — trên máy bạn daemon chưa chạy):

bash — bật Docker 
# Mở app Docker Desktop
open -a Docker

# Chờ ~15-30 giây rồi kiểm tra. In ra số version = daemon đã sẵn sàng.
# Nếu báo "Cannot connect to the Docker daemon" thì chờ thêm rồi chạy lại.
docker info --format '{{.ServerVersion}}'

Bước 4b. Tạo file docker-compose.yml ở thư mục gốc của elearning-api (dùng nút Copy góc phải):

elearning-api/docker-compose.yml 
# File này mô tả HẠ TẦNG của project dưới dạng code.
# Ai clone repo về cũng dựng được y hệt môi trường của bạn bằng 1 lệnh.
services:
  postgres:
    # alpine = bản Linux siêu nhẹ (~80MB thay vì ~400MB)
    image: postgres:18-alpine
    container_name: elearning-postgres
    # Tự bật lại khi Docker Desktop khởi động, trừ khi bạn chủ động stop
    restart: unless-stopped
    environment:
      POSTGRES_USER: elearning
      POSTGRES_PASSWORD: elearning_dev_pw
      POSTGRES_DB: elearning
    ports:
      # "5433:5432" = cổng-trên-máy-bạn : cổng-bên-trong-container.
      # Dùng 5433 vì 5432 đang bị Postgres Homebrew của bạn giữ.
      - "5433:5432"
    volumes:
      # ⚠️ Postgres 18 gắn volume ở /var/lib/postgresql — KHÔNG phải /data (xem cảnh báo dưới)
      - postgres-data:/var/lib/postgresql
    healthcheck:
      # Docker tự gõ lệnh này để biết DB đã SẴN SÀNG NHẬN KẾT NỐI chưa.
      # "container đang chạy" KHÁC "database sẵn sàng" — nhầm chỗ này là app crash lúc khởi động.
      test: ["CMD-SHELL", "pg_isready -U elearning -d elearning"]
      interval: 5s
      timeout: 5s
      retries: 10

  redis:
    image: redis:8-alpine
    container_name: elearning-redis
    restart: unless-stopped
    ports:
      # 6380 thay vì 6379 mặc định, cho đồng bộ với quy ước "+1" ở trên
      - "6380:6379"
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 5s
      retries: 10

# Volume = ổ đĩa ảo do Docker quản lý. Đây là thứ giữ dữ liệu SỐNG SÓT
# khi container bị xoá. Không có nó, `docker compose down` là mất sạch DB.
volumes:
  postgres-data:
  redis-data:
🚨 Cái bẫy tôi đã dính khi verify bài này

Lần đầu tôi viết postgres-data:/var/lib/postgresql/data — đúng như mọi tutorial trên mạng. Container crash-loop, restart liên tục, log báo:

log lỗi thật 
Error: in 18+, these Docker images are configured to store database data
  in a format which is compatible with "pg_ctlcluster"...
  The suggested container configuration for 18+ is to place a single
  mount at /var/lib/postgresql

Image postgres:18 đã đổi điểm gắn volume sang /var/lib/postgresql (biến PGDATA giờ trỏ tới /var/lib/postgresql/18/docker). Mọi hướng dẫn viết trước 2025 đều sai ở đây.

Bài học lớn hơn cái bug: khi container chết, việc đầu tiên luôn là docker compose logs <tên-service>. Container không im lặng chết — nó luôn nói lý do. Đa số người mới đi google trước khi đọc log.

Bước 4c. Khởi động:

bash 
# up = dựng và chạy; -d = detached (chạy nền, trả lại terminal cho bạn)
# Lần đầu sẽ tải image về, mất ~1-2 phút.
docker compose up -d

# Chờ ~20 giây cho database khởi tạo lần đầu, rồi kiểm tra trạng thái
docker compose ps
output thật (đã verify) 
NAME                 STATUS                    PORTS
elearning-postgres   Up 25 seconds (healthy)   0.0.0.0:5433->5432/tcp
elearning-redis      Up 25 seconds (healthy)   0.0.0.0:6380->6379/tcp

Chữ (healthy) mới là thứ bạn cần thấy — không phải chỉ Up. Đó là kết quả của khối healthcheck bạn vừa viết.

5. Sanity check — ba lệnh phải xanh

Đây là bài kiểm tra chứng minh cả bộ máy chạy được. Chạy đủ 3 lệnh:

bash — ✅ check 1: Postgres trả lời từ máy bạn 
# Dùng psql (client Homebrew bạn đã có) nối vào Postgres TRONG container qua cổng 5433.
# PGPASSWORD=... đặt trước lệnh = biến môi trường chỉ sống trong đúng lệnh này.
# Đây là bài test tổng hợp: sai cổng, sai mật khẩu, hay container chưa lên -> đều gãy ở đây.
PGPASSWORD=elearning_dev_pw psql -h localhost -p 5433 -U elearning -d elearning -c "SELECT 1+1 AS sanity;"
phải ra đúng thế này 
 sanity
--------
      2
(1 row)
bash — ✅ check 2: Redis trả lời 
# exec = chạy một lệnh BÊN TRONG container đang chạy.
# redis-cli ping là "cú đấm thử" chuẩn của Redis, phải trả về PONG.
docker compose exec redis redis-cli ping
phải ra 
PONG
bash — ✅ check 3: bộ test của app chạy được 
# Nest sinh sẵn 1 test mẫu. Chạy được nghĩa là toolchain TypeScript + Jest ổn.
# Module 7 sẽ quay lại đây và viết test thật.
cd ~/Documents/fullstack/elearning-api && npm test
phải ra (đã verify) 
Test Suites: 1 passed, 1 total
Tests:       1 passed, 1 total
🧰 Bốn lệnh Docker bạn sẽ dùng suốt khoá — thuộc lòng luôn
  • docker compose up -d — bật hạ tầng (làm mỗi lần khởi động máy)
  • docker compose ps — xem cái gì đang chạy và có healthy không
  • docker compose logs -f postgres — xem log khi có sự cố (-f = theo dõi liên tục)
  • docker compose down — tắt hạ tầng, giữ nguyên dữ liệu. Thêm -v là xoá sạch cả dữ liệu — chỉ dùng khi muốn làm lại từ đầu.

🧠 Kiểm tra nhanh (bấm để có phản hồi ngay)

Câu 1. Bạn chạy docker compose ps, thấy postgres Up 3 seconds nhưng chưa có chữ (healthy). App của bạn khởi động ngay lúc đó và crash vì không nối được DB. Vì sao?
Câu 2. Trong response của curl, ta thấy header X-Powered-By: Express. Điều đó nói lên gì về NestJS?
Câu 3. Bạn muốn xoá sạch database để dựng lại từ đầu vì schema đã rối. Lệnh nào đúng?
✅ Bạn vừa đạt được
  • Có một API NestJS chạy ở localhost:3333, trả lời được curl
  • Có PostgreSQL 18 và Redis 8 chạy trong Docker, cả hai đều healthy
  • Hiểu cổng là gì và vì sao EADDRINUSE xảy ra
  • Biết phân biệt "container Up" và "service sẵn sàng" — và healthcheck giải quyết việc đó
  • Biết bốn lệnh Docker sẽ dùng hằng ngày, và biết lệnh nào nguy hiểm
  • Biết NestJS chạy trên Express, không phải tự viết tầng mạng

6. Câu hỏi tư duy (bắc cầu sang Bài 01)

Bạn vừa gõ curl -i http://localhost:3333 và nhận về vài dòng chữ. Hãy nghĩ kỹ:

Giữa lúc bạn bấm Enter và lúc chữ "Hello World!" hiện ra — chính xác thì cái gì đã đi qua dây mạng? Nó là chữ hay là số nhị phân? Ai quyết định dòng 200 OK phải nằm ở dòng đầu tiên? Và nếu tôi bảo bạn tự tay gõ một HTTP response bằng telnet thì bạn phải gõ gì?

Nếu trả lời được, bạn sẽ không bao giờ còn thấy backend là ma thuật. Bài 01 ta sẽ vứt NestJS sang một bên và tự viết web server bằng node:http thuần — để thấy Nest thực ra đã che giấu cái gì.
