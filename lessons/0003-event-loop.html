Module 1 · Bài 03

Event loop & non-blocking I/O — vì sao Node hợp việc I/O

Cùng một tiến trình, cùng một luồng: một endpoint phục vụ 5 người trong 3 giây, endpoint kia bắt họ xếp hàng 15 giây. Bạn sẽ đo cả hai.

⏱ ~40 phút · 🎯 Mục tiêu: nói được chính xác loại việc nào làm Node đứng hình — và chứng minh bằng số đo của chính bạn, không phải bằng câu chữ học thuộc.

🌉 Bắc cầu từ Bài 02

Cuối Bài 02 tôi hỏi: khi handler đang đứng ở for await đợi body 5MB về, server có phục vụ được người khác không? Và tôi nói cả hai câu trả lời đều nghe hợp lý:

  • "Không" — JavaScript một luồng, đang mắc kẹt thì lấy gì chạy việc khác.
  • "Có" — nếu mỗi upload lớn làm đứng cả server thì đã không ai dùng Node làm backend.

Đáp án: cả hai đều đúng, nhưng cho hai loại "chậm" khác nhau — và gần như mọi người mới đều gộp hai thứ đó làm một. Tách được chúng ra là toàn bộ nội dung bài này. Câu chốt: Node không sợ việc lâu, Node sợ việc bận.

1. Hai loại "chậm" mà ai cũng gộp làm một

Một request mất 3 giây. Nghe thì như nhau, nhưng có hai lý do hoàn toàn khác nhau:

Chờ (I/O)Bận (CPU)
Đang làm gìĐã nhờ người khác làm, ngồi không đợi kết quảTự tay làm, không rảnh một giây nào
Ví dụ thậtQuery database, gọi API bên thứ 3, đọc file, đợi body uploadBăm mật khẩu, resize ảnh, xử lý video, sắp xếp mảng 10 triệu phần tử
Ai thật sự làm việcPostgres / máy khác / đĩa cứng / card mạngChính luồng JavaScript của bạn
Node có rảnh không✅ Rảnh — phục vụ người khác được❌ Không — cả server đứng hình

Cả bài này chỉ để bạn đo thấy dòng cuối cùng của bảng đó. Đừng tin nó vì tôi viết ra — lát nữa bạn sẽ có con số của chính mình.

2. Dựng bàn đo

Tạo file lab/03-event-loop.mjs. Server này có 3 route cố ý rất đơn giản: một cái trả lời ngay (để làm thước đo), một cái chờ 3 giây, một cái tính 3 giây.

elearning-api/lab/03-event-loop.mjs 
import { createServer } from 'node:http';
// Phiên bản setTimeout trả về Promise, để dùng được với await.
import { setTimeout as delay } from 'node:timers/promises';

// Ghi log kèm mốc thời gian tính từ lúc server khởi động,
// để ta ĐO được ai chạy trước ai chứ không phải đoán.
const startedAt = Date.now();
const log = (text) => console.log(`[${String(Date.now() - startedAt).padStart(5)}ms] ${text}`);

const server = createServer(async (request, response) => {
  const url = new URL(request.url, `http://${request.headers.host}`);

  // ── /fast: trả lời ngay, không chờ gì cả ───────────────
  // Đây là THƯỚC ĐO. Nếu nó chậm thì chắc chắn do thứ khác giam luồng.
  if (url.pathname === '/fast') {
    log('/fast -> respond immediately');
    response.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    return response.end('fast\n');
  }

  // ── /io: CHỜ thứ bên ngoài (giả lập query DB 3 giây) ───
  if (url.pathname === '/io') {
    log('/io   -> start WAITING 3s');
    await delay(3000);            // await = "tôi nhả luồng ra, gọi tôi lại khi xong"
    log('/io   -> done waiting, respond');
    response.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    return response.end('io done\n');
  }

  // ── /cpu: TÍNH TOÁN 3 giây, không nhả luồng ────────────
  if (url.pathname === '/cpu') {
    log('/cpu  -> start COMPUTING 3s');
    const start = Date.now();
    while (Date.now() - start < 3000) {
      // Vòng lặp rỗng: CPU quay hết công suất, không có await nào.
      // Đây là chỗ luồng duy nhất của Node bị GIAM.
    }
    log('/cpu  -> done computing, respond');
    response.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    return response.end('cpu done\n');
  }

  response.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  response.end('not found\n');
});

server.listen(3340, () => {
  console.log('Server listening on http://localhost:3340');
});

🔎 Vì sao dùng setTimeout để giả lập database?

Nói cho sòng phẳng: setTimeout là hẹn giờ, không phải I/O thật. Nhưng với event loop thì hai thứ này cư xử y hệt nhau: cả hai đều là "đăng ký một việc cho bên ngoài, nhả luồng ra, quay lại khi có kết quả". Dùng timer để bạn đo được con số chính xác 3 giây mỗi lần chạy, thay vì phụ thuộc vào database hôm nay nhanh hay chậm.

💡 Đọc kỹ con số 7522 — nó là cả bài học

Request /fast tới nơi từ giây thứ 4,8. Nhưng dòng log của nó chỉ hiện ra ở 7522ms — đúng 1 mili-giây sau khi /cpu xong. Không có gì "xử lý chậm" ở đây cả: nó còn chưa được nhìn tới.

5. Đo thông lượng: 3 giây hay 15 giây?

Hai thí nghiệm trên mới có 2 request. Giờ bắn 5 request cùng lúc vào từng route và đo tổng thời gian. Đây là lúc khác biệt trở nên tàn nhẫn:

🚨 Đây là dạng sự cố production bạn sẽ gặp thật

Hình dung API e-learning của bạn có endpoint xuất báo cáo, chạy 3 giây CPU. Ngày thường chẳng ai để ý. Rồi 20 người bấm cùng lúc → người cuối đợi 60 giây, và trong 60 giây đó toàn bộ website chết: trang chủ không load, đăng nhập không được, thanh toán treo. Biểu đồ CPU 100%, log không một dòng lỗi. Đây chính xác là kiểu sự cố mà mission của bạn ghi "debug được sự cố production: chậm ở đâu" — và giờ bạn biết chỗ đầu tiên phải nhìn.

6. Cơ chế: vì sao lại như vậy

Node có một luồng chạy JavaScript. Cái vòng lặp điều phối nó gọi là event loop, và nó chỉ làm đúng một việc, lặp đi lặp lại:

event loop — mô tả bằng lời 
lặp mãi mãi:
  1. Chạy hết code đang có cho tới khi KHÔNG CÒN GÌ để chạy
  2. Nhìn xem có việc nào bên ngoài báo "xong rồi" không
     (timer tới hạn · database trả kết quả · dữ liệu mạng vừa tới)
  3. Lấy việc đó ra, chạy hàm tương ứng
  4. Quay lại bước 1

Chú ý bước 1: "cho tới khi không còn gì để chạy". Event loop không có quyền cắt ngang code của bạn giữa chừng. Nó phải đợi bạn trả luồng lại. Vòng while ở /cpu không bao giờ trả — nên bước 2 không bao giờ tới lượt.

Chứng minh trong 10 dòng. Tạo lab/03-order.mjs:

elearning-api/lab/03-order.mjs 
const startedAt = Date.now();

console.log('1 - synchronous');

// Hẹn 0 mili-giây. Tức là "chạy càng sớm càng tốt".
setTimeout(() => {
  console.log(`4 - timer ran after ${Date.now() - startedAt}ms (we asked for 0ms!)`);
}, 0);

Promise.resolve().then(() => console.log('3 - microtask'));

console.log('2 - also synchronous');

// Giam luồng 2 giây — không nhả cho ai cả.
while (Date.now() - startedAt < 2000) {
}

console.log(`-- blocking loop finished after ${Date.now() - startedAt}ms --`);
bash 
node lab/03-order.mjs
output THẬT (đã verify)

💡 setTimeout(..., 0) không có nghĩa là "chạy sau 0ms"

Nó nghĩa là "xếp hàng, chạy sớm nhất có thể sau khi luồng rảnh". Ở đây luồng bận 2 giây, nên cái hẹn 0ms chạy sau 2000ms. Số 0 là lời hứa sớm nhất, không phải đảm bảo.

Đây chính là lời giải thích cho thí nghiệm B ở quy mô nhỏ: request /fast cũng chỉ là một "việc đang xếp hàng", và nó phải đợi vòng while nhả luồng — y như cái timer này. Thứ tự 3 trước 4 (microtask trước timer) là chi tiết của Bài 04; giờ chỉ cần nhớ: cả hai đều phải đợi code đồng bộ chạy xong.

7. Nửa sự thật còn lại: "bất đồng bộ" không phải lúc nào cũng là event loop

Nếu dừng ở đây bạn sẽ mang theo một hiểu lầm, và nó sẽ cắn bạn ở Bài 22 khi ta băm mật khẩu. Hiểu lầm đó là: "cứ có await thì không chặn".

Một số việc CPU-nặng trong Node có bản bất đồng bộ, và chúng không chạy trên event loop mà chạy trên một nhóm luồng phụ (thread pool) do thư viện libuv quản lý. Docs Node liệt kê rõ những API dùng nhóm luồng này: toàn bộ fs, crypto.pbkdf2(), dns.lookup()… và nói luôn số luồng mặc định là 4.

Con số đo thật, cùng một phép băm mật khẩu 4 triệu vòng:

Chạy gìMấtNói lên điều gì
1 lần, bản Sync1453 msMốc tham chiếu — và nó chặn event loop
4 lần bất đồng bộ cùng lúc1757 msGần bằng một lần → 4 việc chạy song song thật trên 4 luồng
8 lần bất đồng bộ cùng lúc3716 msGấp đôi → 4 cái chạy trước, 4 cái đợi. Nhóm luồng đã đầy.
⚠️ Đừng vội đi chỉnh UV_THREADPOOL_SIZE cho to

Tôi đã thử tăng lên 8 trên máy này: gần như không nhanh hơn (3716ms → 3484ms). Lý do rất đời: thêm luồng không đẻ ra thêm CPU. Máy M1 có 8 nhân nhưng chỉ 4 nhân hiệu năng cao, nên việc CPU-nặng bị chặn bởi phần cứng, không phải bởi con số cấu hình. Bài học: việc CPU-nặng không có chỗ nào để giấu trong một request — cách đúng là đẩy nó ra khỏi vòng đời request, giao cho một hàng đợi xử lý nền. Đó là Bài 37 (BullMQ), và giờ bạn đã biết vì sao bài đó phải tồn tại.

8. Câu hỏi tư duy (bắc cầu sang Bài 04)

Ở phần 6, thứ tự in ra là 1 → 2 → 3 (microtask) → 4 (timer). Cả 3 và 4 đều đợi luồng rảnh, nhưng microtask luôn chạy trước timer, kể cả khi timer đã tới hạn từ lâu. Vì sao lại có hai hàng đợi riêng, và cái nào được ưu tiên?

Câu hỏi thứ hai, nặng ký hơn — và nó nối thẳng vào tai nạn ở Bài 02. Bạn đã thấy lỗi ném ra trong handler async làm chết cả tiến trình. Vậy: khi một Promise bị từ chối mà không ai catch, cái lỗi đó đi đâu? Nó không có try/catch nào bao quanh ở thời điểm nó xảy ra — vì hàm gọi nó đã chạy xong từ lâu và đã rời khỏi stack rồi.

Trả lời được câu đó là bạn hiểu vì sao try/catch quanh một callback không hề bắt được lỗi bên trong callback đó — cái bẫy làm mất rất nhiều giờ debug của người mới chuyển từ frontend sang backend. Bài 04 mổ nó ra.
