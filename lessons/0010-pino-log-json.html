Module 2 · Bài 10

Pino: log JSON cho máy đọc, và tự động che secret

Log của bạn đang viết cho người. Production cần log viết cho máy — và cần một tấm lưới chặn secret lọt vào log.

⏱ ~40 phút · 🎯 Sản phẩm: dev in log gọn dễ đọc, production xuất JSON một dòng lọc được bằng máy, và mọi password / Authorization tự động bị che.

🌉 Bắc cầu từ Bài 09

Cuối Bài 09 tôi có nói: log hiện vẫn là văn bản cho người đọc, và hệ thống thật thường log ra JSON — nhưng tôi hoãn lại vì lúc đó thứ đắt giá nhất (request-id) đã có rồi.

Giờ ta làm nốt. Và có một tin thú vị: thư viện ta sắp dùng hoạt động y hệt cách bạn đã tự viết tay ở Bài 09 — nó cũng dùng AsyncLocalStorage. Bạn sẽ không học một thứ xa lạ, mà là thay bản thủ công của mình bằng bản công nghiệp, và hiểu chính xác nó làm gì bên trong.

1. Vì sao grep không đủ nữa

Ở Bài 09, cách tra log là grep "457f82f2" app.log. Nó hoạt động — cho tới khi gặp ba tình huống rất bình thường:

Tình huốngVới log văn bảnVới log JSON
"Cho tôi mọi lỗi 5xx trong 1 giờ qua" viết regex, và sai sót lọc level >= 50
"Endpoint nào chậm nhất?" gần như không làm được gom theo req.url, tính trung bình
Log nằm trên 5 máy khác nhau ssh vào từng máy mà grep đổ chung vào một chỗ, truy vấn như database
💡 Khác biệt cốt lõi: log là dữ liệu, không phải câu văn

Dòng [457f82f2] Looking up course id=99 với máy chỉ là một chuỗi ký tự — muốn biết "id là 99" phải tự cắt chuỗi. Còn {"req":{"id":"457f82f2"},"msg":"Looking up course id=99"} thì đã là dữ liệu có cấu trúc: máy đọc được trường nào ra trường nấy, lọc và gom nhóm được ngay. Đó là toàn bộ ý nghĩa của chữ "có cấu trúc" trong "structured logging".

Vì production không nên in đẹp: tô màu và xuống dòng làm log to hơn, chậm hơn, và phá vỡ định dạng JSON mà hệ thống thu thập log cần. Nó chỉ tồn tại để mắt bạn đọc được lúc dev. Để nhầm sang dependencies thì bản build production phình lên vô ích.

3. Cấu hình — ba việc trong một chỗ

Sửa src/app.module.ts:

elearning-api/src/app.module.ts 
import { LoggerModule } from 'nestjs-pino';        // ← THÊM
import { randomUUID } from 'node:crypto';          // ← THÊM

// ... trong mảng imports, đặt TRƯỚC CoursesModule:
LoggerModule.forRoot({
  pinoHttp: {
    // ── Việc 1: sinh / tôn trọng request-id ──────────────────
    // Đúng logic bạn tự viết trong middleware ở Bài 09.
    genReqId: (req, res) => {
      const incoming = req.headers['x-request-id'];
      const id =
        typeof incoming === 'string' && incoming.trim() !== ''
          ? incoming
          : randomUUID();
      res.setHeader('x-request-id', id);   // trả lại cho client
      return id;
    },

    // ── Việc 2: CHE secret trước khi ghi ra log ──────────────
    redact: {
      paths: [
        'req.headers.authorization',   // token Bearer
        'req.headers.cookie',          // session
        'req.body.password',
        '*.password',                   // mọi field tên password, ở BẤT KỲ object nào
        '*.jwtSecret',
      ],
      censor: '[DA CHE]',               // chuỗi thay thế
    },

    // ── Việc 3: dev in đẹp, production ra JSON ───────────────
    // undefined = không qua transport nào = pino in JSON thuần (mặc định).
    transport:
      process.env.NODE_ENV === 'development'
        ? {
            target: 'pino-pretty',
            options: {
              singleLine: true,
              translateTime: 'HH:MM:ss',
              // Giấu bớt cho log dev dễ đọc; bản JSON production vẫn giữ ĐỦ.
              ignore: 'pid,hostname,context,req,res,responseTime',
              // Tự dựng dòng hiển thị: [id] [class] nội dung
              messageFormat: '[{req.id}] [{context}] {msg}',
            },
          }
        : undefined,
  },
}),

Rồi bảo Nest dùng logger này trong src/main.ts:

elearning-api/src/main.ts 
// Đổi tên khi import để khỏi đụng với Logger của @nestjs/common
import { Logger as PinoNestLogger } from 'nestjs-pino';   // ← THÊM

// Thay dòng app.useLogger(new AppLogger()) của Bài 09 bằng:
app.useLogger(app.get(PinoNestLogger));
⚠️ Bài 09 của bạn giờ thành thừa — và đó là chuyện tốt

nestjs-pino đã lo cả sinh request-id lẫn gắn id vào mỗi dòng log, nên RequestIdMiddleware và AppLogger bạn viết ở Bài 09 không còn cần thiết. Bạn có thể gỡ chúng khỏi app.module.ts và main.ts.

Nhưng giữ lại file request-context.ts — filter ở Bài 07 vẫn đang gọi getRequestId() để đưa id vào body lỗi. Nếu bạn gỡ middleware thì hàm đó trả undefined; muốn giữ requestId trong body lỗi thì cứ để nguyên middleware chạy song song — nó rẻ, và hai bên dùng chung một id vì cùng đọc từ header.

5. Chạy ở chế độ production — JSON thật

Đổi .env thành NODE_ENV=production, khởi động lại rồi gọi:

bash 
curl -s -o /dev/null -H 'Authorization: Bearer SIEU-BI-MAT' \
  http://localhost:3333/courses/99
một dòng log THẬT (đã tách trường cho dễ nhìn) 
level    : 30
msg      : Looking up course id=99
context  : CoursesService
req.id   : b4f9c602-34f9-4b5c-9fb2-4c7c3dba8b64
req.url  : /courses/99
auth hdr : [DA CHE]        <-- token BỊ CHE, không lọt vào log
🔎 level là số, không phải chữ — và đó là chủ ý

10 trace · 20 debug · 30 info · 40 warn · 50 error · 60 fatal. Dùng số để so sánh được: "cho tôi mọi thứ nghiêm trọng hơn cảnh báo" chỉ là level >= 50. Với chuỗi "error", "fatal" thì bạn phải liệt kê tay và sẽ sót.

6. Phần đáng giá nhất: che secret tự động

Đây là thứ tôi muốn Tuấn nhớ nhất ở bài này. Nhớ Bài 07 — ta cẩn thận không trả chi tiết lỗi ra client. Nhưng có một đường rò rỉ khác, âm thầm hơn nhiều: secret lọt vào log.

một dòng code trông rất vô hại 
// Lập trình viên đang debug, log cả object user ra xem:
this.logger.log({ user });   // user có field password bên trong

Với redact đã cấu hình, kết quả thật khi log một object có password lồng bên trong:

THẬT (đã verify) 
{"email": "a@b.c", "password": "[DA CHE]"}

# Tìm nguyên văn mật khẩu trong toàn bộ file log:
grep -c "MatKhauThat123" app.log   →  0
🚨 Vì sao secret trong log nguy hiểm hơn bạn nghĩ

Log không nằm yên một chỗ. Nó được sao chép đi khắp nơi: gửi lên dịch vụ thu thập log, lưu trữ nhiều tháng, và nhiều người có quyền đọc hơn hẳn số người được đọc database — cả đội dev, cả bên vận hành. Một mật khẩu lọt vào log nghĩa là nó nằm trong bản sao lưu của bên thứ ba, vĩnh viễn.

Và nó xảy ra do tai nạn, không do ác ý: ai đó thêm một dòng logger.log({ user }) lúc 11 giờ đêm để debug rồi quên xoá. redact là tấm lưới đỡ phía dưới — nó không đòi ai phải nhớ điều gì. Chống rò rỉ bằng cơ chế, đừng chống bằng kỷ luật. Chính là tinh thần "liệt kê thứ được phép" ở Bài 06, lần này áp cho đầu ra.

⚠️ Giới hạn thật của redact — đừng tin nó mù quáng

Nó che theo TÊN TRƯỜNG, không hiểu nội dung. Đặt tên pass, pwd, secretKey mà không khai trong paths thì nó không che. Và nếu bạn nhét mật khẩu vào giữa một chuỗi (logger.log(`user=${email} pass=${password}`)) thì redact hoàn toàn bó tay — với nó, đó chỉ là một câu văn.

Vậy nên: log OBJECT, đừng log chuỗi ghép tay. Vừa cho redact có chỗ bám, vừa đúng tinh thần "log là dữ liệu" ở phần 1.

💡 Chỗ này khép lại một vòng từ Bài 08

Biến NODE_ENV bạn khai báo và bắt buộc phải hợp lệ ở Bài 08 — giờ nó có việc thật để làm: quyết định log ra hình dạng nào. Nếu ai đó deploy mà gõ nhầm NODE_ENV=prod, Bài 08 đã chặn ngay từ lúc khởi động. Không có bước đó, bạn sẽ chạy production với pino-pretty mà không hay biết — log không máy nào đọc được, và bạn chỉ phát hiện đúng lúc cần tra sự cố nhất.

8. Câu hỏi tư duy (bắc cầu sang Module 3)

Module 2 khép lại ở đây — API của bạn đã có kiến trúc, validate, lỗi chuẩn hoá, cấu hình an toàn và log truy vết được. Nhưng nhìn lại CoursesService: dữ liệu vẫn là một mảng cứng trong bộ nhớ. Khởi động lại là mọi khoá học tạo bằng POST bốc hơi.

Trước khi thay bằng Postgres, thử tự trả lời: một khoá học có nhiều bài học; một học viên mua nhiều khoá; một khoá có nhiều học viên. Bạn vẽ những bảng nào, và cái quan hệ "nhiều–nhiều" kia để ở đâu?

Câu khó hơn, và nó quyết định cả kiến trúc: khi học viên mua khoá học, giá tiền lưu ở đâu? Lưu trong bảng khoá học thì hôm sau bạn giảm giá — hoá đơn cũ có tự đổi theo không?
