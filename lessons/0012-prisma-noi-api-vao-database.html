🌉 Bài 11 kết bằng hai câu hỏi. Đây là câu trả lời.

Một: "Làm sao thay đổi cấu trúc database đang chạy mà không mất dữ liệu?" → migration: mỗi thay đổi là một file SQL nhỏ, được đánh số và ghi lại là đã chạy chưa.

Hai: "Ai biết database nào đang ở trạng thái nào?" → chính database tự ghi. Prisma tạo bảng _prisma_migrations trong đó, liệt kê những migration đã áp dụng. Hỏi bất kỳ database nào "mày đang ở đâu?" đều có câu trả lời. Đó là lý do người ta gọi migration là git cho cấu trúc database.

1. Prisma làm gì cho bạn — và lấy đi cái gì

Không có Prisma, để đọc một khoá học bạn phải: viết chuỗi SQL, mở kết nối, truyền tham số cho đúng (sai là dính SQL injection), nhận về mảng object không có kiểu, tự đổi current_price thành price. Mỗi bảng làm lại từ đầu.

4. Đặt lại tên cho người đọc — @map

Tên vừa sinh ra là tên của database: courses số nhiều, current_price gạch dưới. Viết trong TypeScript thì lạc lõng. Prisma cho phép dùng một tên trong code, một tên khác dưới database:

Chỉ thịNghĩa
@@map("courses")model Course ↔ bảng courses
@map("current_price")field currentPrice ↔ cột current_price
prisma/schema.prisma — sửa lại model Course 
model Course {
  id           BigInt       @id @default(autoincrement())
  title        String
  level        String
  // Trong code gọi là currentPrice; dưới DB vẫn là cột current_price.
  currentPrice Decimal      @map("current_price") @db.Decimal(12, 0)
  createdAt    DateTime     @default(now()) @map("created_at") @db.Timestamptz(6)
  lessons      Lesson[]
  orderItems   OrderItem[]
  enrollments  Enrollment[]

  // @@map = tên BẢNG dưới database. Không có dòng này Prisma sẽ đi tìm bảng "Course".
  @@map("courses")
}
💡 Ba dòng lessons, orderItems, enrollments — vì sao chúng KHÔNG có @map

Vì chúng không phải cột. Đó là quan hệ — Prisma sinh ra để bạn đi từ Course sang Lesson trong code. Dưới database không có cột nào tên lessons cả (thứ tồn tại thật là lessons.course_id ở bảng bên kia). Không có cột thì không có gì để ánh xạ, nên không cần @map.

Kiểm chứng: so hai schema chỉ khác đúng tên field quan hệ, xem Prisma sinh ra SQL gì:

kết quả THẬT — đổi tên field quan hệ 
-- This is an empty migration.

Đối chứng — bỏ @map khỏi currentPrice, một field thật:

kết quả THẬT — và đây là mất dữ liệu 
ALTER TABLE "courses" DROP COLUMN "current_price",
ADD COLUMN "currentPrice" DECIMAL(12,0) NOT NULL;

DROP COLUMN — bay sạch cột giá. Đó chính là lý do field thật bắt buộc phải có @map, còn quan hệ thì không.

5. PrismaService — cắm Prisma vào vòng đời NestJS

Prisma cần mở kết nối lúc app khởi động và đóng lúc app tắt. Nest có sẵn hai móc cho việc đó. Bọc PrismaClient thành một service để Nest tiêm được vào mọi nơi:

src/prisma/prisma.service.ts 
import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
// Prisma 7 sinh client vào dự án, không phải node_modules — nhớ đường dẫn tương đối.
import { PrismaClient } from '../generated/prisma/client';

// extends PrismaClient = service này CÓ SẴN mọi phương thức truy vấn (.course, .user...).
// Nhờ vậy nơi khác chỉ cần tiêm PrismaService, không phải tự new PrismaClient.
@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  constructor() {
    // Từ Prisma 7, PrismaClient KHÔNG tự kết nối nữa — phải đưa "driver adapter",
    // tức là trình điều khiển Postgres thật sự đứng ra mở socket.
    super({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) });
  }

  // Nest gọi hàm này SAU khi module đã dựng xong — mở kết nối ở đây.
  async onModuleInit() {
    await this.$connect();
  }

  // Và gọi hàm này khi app tắt — trả kết nối về cho Postgres cho sạch.
  async onModuleDestroy() {
    await this.$disconnect();
  }
}

6. Thay mảng giả bằng database thật

src/courses/courses.service.ts 
@Injectable()
export class CoursesService {
  private readonly logger = new Logger(CoursesService.name);

  // Không còn mảng courses trong bộ nhớ. Dữ liệu sống trong Postgres.
  constructor(private readonly prisma: PrismaService) {}

  // Mọi truy vấn đều là async — nó đi qua mạng tới Postgres (Bài 03: I/O).
  async findAll(level?: string) {
    return this.prisma.course.findMany({
      // where: undefined = không lọc. Prisma bỏ qua field undefined,
      // nên một dòng này lo cả hai trường hợp có/không có ?level=
      where: level ? { level } : undefined,
      orderBy: { id: 'asc' },
    });
  }

  async findOne(id: number) {
    this.logger.log(`Looking up course id=${id}`);
    // findUnique chỉ tìm theo cột có UNIQUE/PRIMARY KEY — nhanh và rõ ý.
    // BigInt(id) vì cột id là BIGINT: JS number không mang nổi số lớn cỡ đó.
    const course = await this.prisma.course.findUnique({ where: { id: BigInt(id) } });

    // Ném exception y như cũ — Bài 07 lo phần biến nó thành 404.
    if (!course) throw new NotFoundException(`Course with id=${id} not found`);

    return course;
  }
}

💡 Vì sao BigInt không chuyển thành JSON được

JSON là chuẩn ra đời trước kiểu BigInt của JavaScript, nên không có chỗ cho nó — JSON.stringify ném lỗi thay vì đoán bừa. Cùng vấn đề với Decimal (kiểu Prisma dùng cho NUMERIC, chính là thứ giữ tiền chính xác ở Bài 11).

Bài học rộng hơn: đừng trả thẳng object của tầng database ra API. Hai thứ đó là hai hợp đồng khác nhau — đổi tên cột không được phép làm hỏng response của khách.

Tách một hàm chuyển đổi. Đây cũng là chỗ trả lại đúng tên price mà API vẫn dùng:

src/courses/utils/to-course-response.ts 
import type { CourseModel } from '../../generated/prisma/models';
import type { Course } from '../course.interface';

// Dịch từ "hàng lấy dưới DB lên" sang "thứ API hứa trả cho khách".
export function toCourseResponse(row: CourseModel): Course {
  return {
    id: Number(row.id),                    // BigInt → number
    title: row.title,
    level: row.level,
    price: row.currentPrice.toNumber(),      // Decimal → number
    createdAt: row.createdAt.toISOString(),  // Date → chuỗi ISO
  };
}
src/courses/courses.service.ts — dùng hàm chuyển đổi 
  async findAll(level?: string): Promise<Course[]> {
    const rows = await this.prisma.course.findMany({
      where: level ? { level } : undefined,
      orderBy: { id: 'asc' },
    });

    return rows.map(toCourseResponse);
  }
⚠️ Number(row.id) — an toàn tới khi nào?

number của JS giữ chính xác được số nguyên tới khoảng 9 triệu tỷ. Với bảng khoá học thì thoải mái. Nhưng đây là một giả định, không phải chân lý — hệ thống nào có id vượt ngưỡng đó thì phải trả id dạng chuỗi. Biết mình đang giả định cái gì, đó mới là khác biệt.

Giờ tạm gỡ @IsIn khỏi CreateCourseDto (thay bằng @IsString()) — giả lập tình huống ai đó viết code cẩu thả, hoặc một script chạy tay đi vòng qua API. Gửi lại đúng request đó:

# trong log:

💡 Đây là bằng chứng cho toàn bộ Bài 11

Prisma không biết ràng buộc courses_level_check tồn tại — nó đã cảnh báo đúng như thế ở mục 3. Vậy mà dữ liệu bẩn vẫn không vào được. Vì ràng buộc sống trong database, và mọi con đường đều phải đi qua database.

Chú ý sự khác nhau về chất lượng: DTO cho 400 kèm câu giải thích cho người dùng; database cho 500 khô khốc. Nên: DTO là lớp giao tiếp, ràng buộc DB là lớp không ai đi vòng được. Cần cả hai, và chúng làm hai việc khác nhau. Nhớ gắn @IsIn trở lại sau khi thử xong.

9. Migration — git cho cấu trúc database

Database của bạn đã có sẵn 6 bảng và dữ liệu thật, nhưng Prisma thì chưa biết gì về lịch sử đó. Chạy thẳng migrate dev lúc này, Prisma thấy database "lạ" và có thể đòi xoá sạch làm lại. Phải nói cho nó biết trước: "trạng thái hiện tại coi như đã áp dụng rồi". Bước đó gọi là baseline.

bash — baseline, chỉ làm MỘT LẦN trong đời dự án 
# 1. Sinh file SQL mô tả toàn bộ schema hiện tại
mkdir -p prisma/migrations/0_init
npx prisma migrate diff \
  --from-empty --to-schema prisma/schema.prisma --script \
  > prisma/migrations/0_init/migration.sql

# 2. Đánh dấu "migration này coi như đã chạy rồi" — KHÔNG thực thi nó
npx prisma migrate resolve --applied 0_init
kết quả THẬT 
Migration 0_init marked as applied.

$ npx prisma migrate status
1 migration found in prisma/migrations
Database schema is up to date!
⚠️ Cờ này vừa đổi tên ở Prisma 7

Bài viết cũ dùng --to-schema-datamodel. Prisma 7 đổi thành --to-schema, và báo lỗi thẳng nếu bạn gõ tên cũ. Tôi đã đâm đúng vào đấy khi soạn bài.

Một — thêm cột NOT NULL vào bảng đã có dữ liệu là hỏng. Postgres hỏi: 3 dòng đang có thì điền gì vào cột mới? Không trả lời được thì nó từ chối. Cách đúng: thêm cột cho phép NULL (String?), điền dữ liệu dần, rồi mới siết lại.

Hai — migrate dev chỉ dùng ở máy mình. Trên production dùng prisma migrate deploy: nó chỉ áp dụng file có sẵn, không tự sinh, không bao giờ đòi reset. Gõ nhầm dev trên production là chuyện kể lại cả đời. Bài 17 sẽ đào sâu.

Ba — migration Prisma sinh ra không đầy đủ bằng SQL bạn viết ở Bài 11. Tôi đã đếm trong file 0_init vừa sinh:

so sánh THẬT — schema.sql của bạn vs migration Prisma sinh 
Giữ được:  6 FOREIGN KEY · 3 ON DELETE CASCADE · 3 ON DELETE RESTRICT · 4 UNIQUE

MẤT:       5 ràng buộc CHECK          (level, giá ≥ 0, status...)
           GENERATED ALWAYS AS IDENTITY  → thay bằng BIGSERIAL (tự gán id được)

Trên database hiện tại của bạn thì 5 ràng buộc CHECK vẫn còn nguyên (tôi đã kiểm lại sau khi migrate) — vì migration chỉ chạy đúng câu ALTER TABLE kia. Nhưng chúng không nằm trong lịch sử migration. Ai dựng database mới từ đầu bằng migrate deploy sẽ có một database yếu hơn của bạn, và không ai nhận ra. Cách xử lý: tự tay thêm CHECK vào file migration — file SQL đó sửa được, và bạn nên sửa. Đây là lúc biết SQL thuần trả tiền lại cho bạn (Module 3.5).

const courses = await prisma.course.findMany();          // 1 truy vấn

for (const course of courses) {
  course.lessons = await prisma.lesson.findMany({          // 1 truy vấn MỖI khoá
    where: { courseId: course.id },
  });
}
